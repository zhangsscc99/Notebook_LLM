01

memory 的本质是什么

OpenClaw 里的 memory 不是隐藏在模型内部的“神秘长期记忆”。它的本质非常工程化：

把重要信息写到磁盘文件。
把文件切成可检索的 chunks。
建立全文索引与语义索引。
通过 memory_search / memory_get 再把需要的内容取回来。
也就是说：只有真正落盘的东西，才算“被记住”。
参考：docs/concepts/memory.md:9-11

memory 里到底存什么

MEMORY.md

长期记忆。适合放稳定偏好、长期决策、持续有效的事实。

memory/YYYY-MM-DD.md

日记式工作层。适合会话摘要、当天观察、上下文碎片。

DREAMS.md

可选。用于 dreaming / promotion / review 相关输出。

extraPaths

配置里可以补充额外可索引目录，让记忆范围超出默认工作区。

搜索一次 memory，大概发生了什么

先检查有没有索引；没有就尝试 sync。
做 query 预处理与 preflight。
如果需要，初始化 embedding provider。
跑 keyword / vector / hybrid 检索。
做 merge、score、filter，然后返回结果。
extensions/memory-core/src/memory/manager.ts
async search(query, opts) {
  if (!hasIndexedContent) await sync(...)
  const preflight = resolveMemorySearchPreflight(...)
  if (preflight.shouldInitializeProvider) await ensureProviderInitialized()
  ... run search ...
}
这就是为什么 memory search 不是“grep 一下文本”——它其实是带索引、带 provider、带 fallback 的完整 retrieval pipeline。

vector search 是怎么做的

如果 sqlite-vec 可用，系统会直接走原生向量 KNN；如果不可用，就退化为读取已保存 embedding，再在进程内做 cosine similarity。

if (await ensureVectorReady(...)) {
  // sqlite-vec native KNN
} else {
  // fallback: parse embeddings + cosineSimilarity
}

所以它不是“没有向量扩展就完全废掉”，而是会优雅降级。

没有索引的时候 sync 是干啥的

在 memory_search 里，如果数据库里还没有任何 chunk，代码会先强制跑一次同步：

if (!hasIndexedContent) {
  await this.sync({ reason: "search", force: true });
}

这里的 sync 不是“同步模型记忆”，而是把磁盘上的 memory 文件整理成可搜索索引。它主要做这些事：

  • 扫描 MEMORY.md、memory/*.md、extra paths，以及可选 session transcript。
  • 读取文件内容，计算 hash、mtime、size，判断哪些文件新增、修改或删除。
  • 把 Markdown 切成 chunks，写入 chunks 表。
  • 更新 FTS 全文索引，让关键词搜索能工作。
  • 如果 embedding provider 可用，就为 chunk 生成 embedding，并写入 vector/embedding 相关存储。
所以第一次搜索前没有索引时，sync 的作用就是“现场建索引”，避免刚启动后第一次搜索直接返回空结果。
参考：extensions/memory-core/src/memory/manager.ts:315-325、extensions/memory-core/src/memory/manager-sync-ops.ts
15

preflight 是什么

preflight 是搜索真正执行前的一道轻量检查。它不查数据库、不调用 embedding provider，只判断这次搜索有没有必要继续。

const normalizedQuery = query.trim();
if (!normalizedQuery) shouldSearch = false;
if (!hasIndexedContent) shouldSearch = false;
otherwise shouldSearch = true and shouldInitializeProvider = true;

在当前实现里，preflight 只做三件事：

  • 把 query 前后空白 trim 掉。
  • 如果 query 为空，就不搜索，也不初始化 provider。
  • 如果没有任何已索引内容，就不搜索，也不初始化 provider。

只有 query 非空且已有索引内容时，它才允许继续搜索，并告诉上层可以初始化 embedding provider。

它的工程价值是避免无意义成本：空 query 或空索引时，不需要启动 embedding provider，也不需要跑 FTS/vector 查询。
参考：extensions/memory-core/src/memory/manager-search-preflight.ts:1-31、extensions/memory-core/src/memory/manager.ts:327-347
16

FTS 虚表是什么

FTS 是 SQLite 的 Full Text Search，全文搜索。所谓“虚表”就是 SQLite 里的 virtual table：它看起来像普通表，可以查询，但底层由扩展模块维护特殊索引结构。

OpenClaw 创建的 FTS 虚表大概长这样：

CREATE VIRTUAL TABLE chunks_fts USING fts5(
  text,
  id UNINDEXED,
  path UNINDEXED,
  source UNINDEXED,
  model UNINDEXED,
  start_line UNINDEXED,
  end_line UNINDEXED
);

这里真正参与全文搜索的是 text。其他字段标成 UNINDEXED，意思是它们只是跟结果一起返回的元数据，不参与倒排索引。

它解决的是关键词搜索问题，比如错误码、配置键、文件名片段、精确术语。vector search 擅长语义相似，但对精确字符串不一定可靠；FTS 则补上这个短板。

所以 hybrid search 里的 “BM25/keyword path” 就依赖 FTS 虚表。它让 memory_search 不只是语义相似搜索，也能找精确词。
参考：packages/memory-host-sdk/src/host/memory-schema.ts:59-82、extensions/memory-core/src/memory/manager-search.ts

memory_get 工具详解

memory_get 的定位不是搜索，而是按路径精确读取一段记忆文件。通常流程是先用 memory_search 找到相关片段，再用 memory_get 拉取更完整、可核对的原文行。

它的参数很少：

  • path：必填，要读取的 memory 文件路径。
  • from：可选，从第几行开始读。
  • lines：可选，读取多少行。
  • corpus：可选，memory、wiki、all。
MemoryGetSchema = {
  path: string,
  from?: number,
  lines?: number,
  corpus?: "memory" | "wiki" | "all"
}

执行时会先解析当前 agent 和配置。如果 memory search 被禁用，工具不会被创建。真正执行时，它按 corpus 和 backend 分支：

  • corpus=wiki：直接去 registered corpus supplement 里读，比如 memory-wiki。
  • builtin backend：调用 readAgentMemoryFile，再进入 readMemoryFile。
  • qmd backend：先拿 MemorySearchManager，再调用它的 readFile。
  • corpus=all：如果 memory 文件读取失败，会尝试从 supplement 里 fallback。

它返回的核心结果是：

{
  path: string,
  text: string,
  from?: number,
  lines?: number,
  truncated?: true,
  nextFrom?: number
}
memory_get 的关键点是“安全精确读取”：它不会全量暴力读取所有 memory，也不会随便读 workspace 里任意文件。
参考：extensions/memory-core/src/tools.ts:391-459、extensions/memory-core/src/tools.shared.ts:38-44、packages/memory-host-sdk/src/host/read-file.ts:48-156

每次记忆检索全流程

一次完整的“记忆检索”通常不是单个动作，而是 memory_search 和 memory_get 的组合。

工具可用性检查：memory-core 注册工具时，会确认当前 agent 配置里 memorySearch 没被禁用。
模型先调用 memory_search，传入自然语言 query，例如“之前我们怎么配置 QMD”。
系统拿到 active memory manager。如果 backend 是 QMD，就走 QMD manager；否则走 builtin SQLite manager。
如果索引为空，先强制 sync({ reason: "search", force: true })，把磁盘文件建成可搜索索引。
执行 preflight：空 query 或无索引内容直接停止，避免无意义 provider 初始化和查询。
如果可以搜索，初始化 embedding provider，然后并行/组合执行 FTS keyword search 和 vector search。
把 keyword 和 vector 结果做 hybrid merge，应用 minScore、maxResults、MMR、temporal decay 等策略。
工具返回候选片段，包括 path、startLine、endLine、score、snippet、source。
模型再用 memory_get 按 path/from/lines 读取原文，避免只凭 snippet 回答。

所以实际链路可以理解为：

user question
  -> memory_search(query)
  -> manager.search()
  -> sync if needed
  -> preflight
  -> FTS + vector retrieval
  -> hybrid merge
  -> search results
  -> memory_get(path, from, lines)
  -> exact excerpt
  -> answer with grounded context
RAG 通常对应第 2 到第 8 步；而 OpenClaw 还额外强调第 9 步，也就是用 memory_get 回读原文，降低只看片段摘要造成的误判。
参考：extensions/memory-core/src/tools.ts、extensions/memory-core/src/memory/manager.ts:302-491、packages/memory-host-sdk/src/host/read-file.ts
19

记忆一共有哪些，除了 RAG

如果把 RAG 理解成“搜索索引，然后把相关片段取回上下文”，那 OpenClaw 的 memory 体系里还有几类不是单纯 RAG 的记忆。

Bootstrap Memory

启动新会话时，系统会把 MEMORY.md 和最近几天的 daily memory 以受限预算注入上下文。这不是搜索，而是启动时的基础记忆。

Exact Read Memory

memory_get 按文件和行号读取原文。它不是语义检索，而是精确回读。

Session Memory

可选地把历史 session transcript 建索引，让后续能搜索以前的对话。它属于会话历史召回。

Memory Flush

compaction 前自动提醒模型把重要内容写进 memory/YYYY-MM-DD.md，这是防止上下文压缩丢信息的写入机制。

Dreaming / Promotion

后台整理短期信号，把高价值内容候选提升到长期记忆，并把审阅信息写到 DREAMS.md。

Memory Wiki

memory-wiki 把 durable memory 编译成更像知识库的结构，有 claims、evidence、dashboard、wiki_search、wiki_get。

换句话说，OpenClaw 的记忆不是只有“RAG 搜索”。它至少包括：

  • 启动注入型记忆：直接进入 prompt。
  • 检索型记忆：memory_search。
  • 精确读取型记忆：memory_get。
  • 会话历史型记忆：session transcript indexing。
  • 自动写入型记忆：memory flush。
  • 整理晋升型记忆：dreaming / promotion。
  • 知识库型记忆：memory-wiki。
  • 外部补充语料：registered corpus supplements。
RAG 是 recall 的一部分，但 OpenClaw 的 memory 更像一个“写入、启动注入、搜索、精读、整理、晋升、知识库化”的完整生命周期。
参考：docs/concepts/memory.md、src/auto-reply/reply/startup-context.ts、extensions/memory-core/src/flush-plan.ts、docs/plugins/memory-wiki.md

QMD 是什么

QMD 不是 memory 文件本身，也不是某一个 embedding 模型。它是 OpenClaw 可选的本地优先搜索 sidecar / 后端引擎：OpenClaw 把要检索的记忆、额外目录、可选 session transcript 交给 QMD 建 collection，然后通过 qmd search、qmd query 等子进程接口取回结果。

和 builtin 后端的区别

builtin 后端是在 OpenClaw 进程内用 SQLite、FTS、向量索引维护 memory。QMD 后端则把索引更新、BM25 搜索、向量搜索、reranking、query expansion 交给外部 qmd 工具处理。

默认模式不是语义搜索

OpenClaw 的 QMD 默认 searchMode 是 search，也就是 BM25 词法搜索。这个模式下它不会主动维护 semantic embedding。只有 vsearch 或 query 才会进入更语义化的路径。

QMD home 和 collection

启用后，OpenClaw 会在 ~/.openclaw/agents/<agentId>/qmd/ 下管理 QMD home，并从 MEMORY.md、memory/、配置的额外路径、可选 session transcript 创建 collection。

失败时的行为

如果 QMD 不可用、二进制缺失或 sidecar 失败，OpenClaw 会回退到 builtin SQLite memory engine，避免单次 QMD 故障直接让 memory 搜索完全不可用。

启用 QMD 的最小配置类似这样：

{
  memory: {
    backend: "qmd"
  }
}
一句话：QMD 是“把 memory 检索外包给一个更强的本地搜索引擎”。它可以做 BM25、vector search、reranking、query expansion，也可以索引 workspace memory 之外的本地资料。
参考：docs/concepts/memory-qmd.md、packages/memory-host-sdk/src/host/backend-config.ts

embedding 模型用的是啥

这里没有一个全局固定答案，取决于你走的是 builtin memory 后端 还是 QMD 后端，以及配置里的 provider / model 怎么设。

builtin 后端

builtin memory 的 embedding 配置在 agents.defaults.memorySearch。如果显式设置 provider 和 model，就用你指定的模型；如果 model 为空，就用该 provider adapter 的默认模型。

auto provider

如果 provider 是 auto 或没有显式设置，OpenClaw 会按可用性选择 provider：local、github-copilot、openai、gemini、voyage、mistral、deepinfra、bedrock 等。ollama 支持但通常需要显式配置。

local 默认模型

本地 embedding adapter 的默认模型是 hf:ggml-org/embeddinggemma-300m-qat-q8_0-GGUF/embeddinggemma-300m-qat-Q8_0.gguf。文档也把它简称为 embeddinggemma-300m-qat-Q8_0.gguf。

OpenAI 示例模型

OpenClaw 配置文档里的 OpenAI 示例使用 text-embedding-3-small。这不是所有安装的强制默认值，而是显式选择 OpenAI provider 时常见的配置示例。

memory 生命周期全图

OpenClaw memory 的生命周期不是单个“检索函数”，而是一条从写入、建索引、搜索、回读、上下文保全、后台整理组成的链路。

信息先落到可审计的文件或 transcript：MEMORY.md、memory/YYYY-MM-DD.md、可选 session transcript、QMD extra paths。
sync 扫描文件，计算 hash / mtime / size，判断哪些文件新增、变化、删除。
文件被切成 chunk，记录 path、source、startLine、endLine、hash、text。
builtin 后端写 SQLite 表、FTS 虚表、可选 sqlite-vec 向量表；QMD 后端写 QMD collection。
模型需要旧信息时调用 memory_search 召回候选片段。
如果需要核对原文，再用 memory_get 按 path/from/lines 精确读取。
临近 compaction 时，memory flush 让模型把 durable 信息追加到当天 memory 文件。
dreaming / promotion 后台整理短期信号，产生候选长期记忆或 dream report。
最重要的源码阅读顺序：先看 tool 入口，再看 manager.search，再看 sync/indexFile/writeChunks，最后看 flush 和 dreaming。

builtin SQLite 表结构

builtin memory index 的核心数据在 SQLite。它不是只存一堆文本，而是把文件状态、chunk、FTS、embedding cache、可选 vector table 分开维护。

meta

存索引元数据，例如 provider/model、chunk 参数、vector 维度、FTS tokenizer、scope hash。用于判断是否需要 full reindex。

files

按 path 记录文件 hash、mtime、size、source。sync 用它判断文件是否变了，以及哪些旧文件已经不存在。

chunks

每个 chunk 一行：id、path、source、start_line、end_line、hash、model、text、embedding、updated_at。它是搜索结果和 memory_get 行号的基础。

chunks_fts / chunks_vec

chunks_fts 是 FTS5 虚表；chunks_vec 是 sqlite-vec 虚表，只有 vector enabled 且扩展可用时创建。

meta
files(path, source, hash, mtime, size)
chunks(id, path, source, start_line, end_line, hash, model, text, embedding, updated_at)
chunks_fts(text, id, path, source, model, start_line, end_line)
chunks_vec(id, embedding)
研究表结构时重点看两件事：source 字段如何区分 memory / sessions，以及 model 字段如何避免不同 embedding 模型的索引混在一起。

chunking 规则

chunking 的目标是把 markdown / transcript 切成适合 embedding 和检索的片段，同时保留原始行号，方便后续 memory_get 回读。

按 token 预算估算字符

chunkMarkdown 根据 chunking.tokens 和内部字符估算上限决定每块大小，不是直接调用 tokenizer 精确切。

支持 overlap

每次 flush 一个 chunk 后，会按 chunking.overlap 保留尾部内容到下一块，减少跨 chunk 信息断裂。

保留 startLine / endLine

每个 chunk 都记录起止行。session transcript 会先转成文本，再用 lineMap 把内容行号 remap 回原 transcript 行。

CJK 长行处理

对中文、日文等 CJK-heavy 长文本，代码会做更细的切分，并避免切断 UTF-16 surrogate pair。

源码核心流程可以简化成：

content.split("\\n")
for each line:
  split long line into segments
  if current chunk exceeds budget:
    flush()
    carryOverlap()
  append segment with lineNo
flush()

FTS + vector 混合排序

builtin search 不是简单“只搜向量”。它优先做 hybrid：关键词 FTS 和向量相似度各自产生候选，然后合并、去重、加权排序。

preflight 清洗 query，并确认索引里有内容。
如果 provider 不可用，就进入 FTS-only 模式，只查 chunks_fts。
如果 provider 可用，先查 FTS 候选，再把 query embed 成向量查 vector 候选。
按 chunk id 合并结果，同一个 chunk 同时保留 vectorScore 和 textScore。
最终分数大致是：vectorWeight * vectorScore + textWeight * textScore。
之后可继续应用 temporal decay 和 MMR，让结果兼顾新近度和多样性。

FTS query 本身会把 query 里的词提取出来，构造成 quoted AND 查询；BM25 rank 会被转成 0 到 1 附近的可合并分数。

研究排序时不要只看 searchVector。真正的排序入口在 mergeHybridResults，还要看 mmr.ts 和 temporal-decay.ts。

memory 写入机制

OpenClaw 的 memory 写入分两类：一类是用户或模型把内容写进 durable memory 文件，另一类是索引器把文件内容写进搜索 index。这两件事不要混在一起。

durable 文件写入

真正长期保留的信息应该追加到 memory/YYYY-MM-DD.md 或维护在 MEMORY.md。memory flush 明确要求 append，不要覆盖。

pre-compaction flush

临近 compaction 时，OpenClaw 可运行 silent memory flush，让模型把本轮值得长期保存的信息写到当天 memory 文件；如果没东西保存则返回 silent token。

索引写入

sync 后 indexFile 会 chunk 文件、生成 embedding、写 chunks、chunks_fts、可选 chunks_vec。

后台整理写入

dreaming / promotion 会记录短期召回信号和 dream report，把可能有价值的信息整理成候选长期记忆。

判断“写 memory”是哪一种：如果写的是 markdown 文件，那是 durable memory；如果写的是 SQLite/QMD，那是检索索引，可以重建。

memory 安全边界

Memory 系统的安全边界主要是：哪些内容会被索引、哪些内容能被工具读、哪些内容会进入 prompt。

索引边界

默认只索引 workspace 的 MEMORY.md 和 memory/，以及配置允许的 extra paths / sessions。watcher 会跳过 .git、node_modules、虚拟环境、缓存目录等。

读取边界

memory_get 不是任意文件读取器。它按受控 memory path、QMD collection prefix 或 registered corpus supplement 读取，并限制行号范围。

session 可见性

session transcript 搜索会经过 filterMemorySearchHitsBySessionVisibility，避免把不该暴露的会话结果直接返回。

失败要显式暴露

embedding quota、provider 错误、FTS/vector 不可用时，工具会返回 disabled/unavailable/debug 信息，调用方不应该假装 memory 搜索成功。

安全上最值得查的不是“能不能搜到”，而是“这个来源是否应该被索引、是否应该被当前 session 看见、是否应该被注入上下文”。

被问 OpenClaw 怎么搞记忆时怎么答

如果别人问“OpenClaw 是怎么搞记忆的”，不要回答成“它有 RAG”这么浅。更准确的回答是：

OpenClaw 的记忆是文件驱动的长期记忆系统。重要信息先写进 MEMORY.md 或 memory/YYYY-MM-DD.md 这类可审计文件，然后 memory-core 或 QMD 把这些文件切成 chunks、建立 FTS/向量索引。模型需要旧信息时先用 memory_search 检索相关片段，再用 memory_get 按路径和行号回读原文。临近 compaction 时还有 memory flush，把当前会话里值得长期保存的信息追加到当天 memory 文件。

你可以按场景用下面三种说法。

30 秒版本

OpenClaw 不是把记忆藏在模型脑子里，而是把记忆显式写成文件。然后它对这些文件建索引，搜索时召回片段，需要核实时再按行读取原文。所以它的 memory 是“文件落盘 + 索引检索 + 原文回读 + compaction 前保全”。

源码版本

工具入口是 memory_search 和 memory_get。它们通过 getMemorySearchManager 拿到 backend manager。builtin 后端是 MemoryIndexManager，用 SQLite、FTS5、可选 sqlite-vec；QMD 后端是 QmdMemoryManager，把检索交给 qmd sidecar。

和普通 RAG 的区别

RAG 只是其中的检索部分。OpenClaw 还包括启动注入、memory flush、session transcript indexing、dreaming / promotion、memory-wiki、registered corpus supplements，以及 memory_get 这种精确原文读取。

一句话判断重点

问“它记住了吗”时，关键不是模型有没有印象，而是信息有没有落盘、有没有被 sync 建索引、搜索结果能不能通过 memory_get 找回原文。

推荐你实际回答时按这个结构：

1. 先说本质：文件驱动，不是模型内部魔法记忆。
2. 再说流程：写文件 -> sync -> chunk -> FTS/vector/QMD index -> memory_search -> memory_get。
3. 再说后端：默认 builtin SQLite/FTS/vector；也可以切到 QMD。
4. 再说扩展：compaction 前 flush，session memory，dreaming，memory-wiki。
5. 最后强调边界：只有落盘并被允许索引/读取的内容，才算可用记忆。
最稳的短答：OpenClaw memory = durable markdown files + searchable index + exact source readback + lifecycle automation。这个答案比单说“RAG”准确得多。

Markdown memory 文件到底干啥

不是。Markdown memory 文件不只是 RAG 之后用来验证全文。它们是 OpenClaw memory 的源数据 / source of truth。RAG index、FTS、vector、QMD collection 都是从这些文件派生出来的缓存或检索结构。

1. 长期记忆的真实载体

MEMORY.md 存 curated long-term memory：稳定事实、偏好、长期决策、短摘要。memory/YYYY-MM-DD.md 存 daily notes：当天上下文、观察、会议/任务记录、较详细的临时知识。

2. 启动上下文来源

MEMORY.md 会作为主长期记忆在主私聊 session 启动时进入上下文，受 bootstrap budget 限制。daily memory 更适合按需检索，避免把所有日志都塞进每次 prompt。

3. 搜索索引的原材料

sync 会扫描这些 Markdown 文件，切成 chunks，写入 SQLite chunks、chunks_fts、可选 chunks_vec；如果用 QMD，就创建/更新 QMD collection。

4. memory_get 的原文来源

memory_search 返回的是片段和行号，memory_get 再按 path/from/lines 回到 Markdown 文件读原文。这确实用于核对 RAG 结果，但只是它的其中一个用途。

5. flush 的写入目标

compaction 前的 memory flush 会要求模型把重要信息追加到 memory/YYYY-MM-DD.md，不是写到向量库本身。向量库之后可以由 sync 重建。

6. 人类可审计和可编辑

因为是普通 Markdown，你可以直接打开、编辑、review、删掉错误记忆。索引只是服务检索；真正该信任和维护的是文件内容。

所以正确关系是：

Markdown memory files
  = durable source of truth
  -> sync/chunk
  -> FTS/vector/QMD index
  -> memory_search returns snippets
  -> memory_get reads original Markdown lines
  -> model answers with verified context
结论：Markdown 文件不是“RAG 后的全文验证附件”。它们是 OpenClaw 记忆的正本。RAG index 是从正本生成的检索视图；memory_get 是回到正本核对和读取更多上下文。

RAG 后会不会读完整相关内容

会，但要说精确一点：OpenClaw 提供了 memory_get 工具让模型在 memory_search 之后读取相关原文；是否调用取决于模型/提示策略和问题是否需要核对。

模型先调用 memory_search(query)。这一步就是 RAG/recall：从 FTS、vector 或 QMD index 里找相关 chunks。
搜索结果会带回 path、startLine、endLine、snippet、score、source/corpus 等信息。
如果 snippet 不够、需要上下文、需要引用原文、或者要避免误读，模型应该继续调用 memory_get(path, from, lines)。
memory_get 回到 Markdown 文件或 QMD collection root，按行读取受限 excerpt。
如果返回 truncated 或 nextFrom，模型可以再次调用 memory_get 继续读后续内容。

不是自动把全文塞进上下文

RAG 搜索不会默认把整个 Markdown 文件全部注入。它先返回相关片段，避免浪费 token。全文或更大范围内容需要通过 memory_get 按需读取。

它知道怎么读，因为工具结果给了坐标

memory_search 的结果包含 path 和行号。模型可以直接把这些坐标传给 memory_get，例如从 startLine 附近多读几十行。

读取也是受限的

memory_get 默认读取有行数和字符预算，默认行数约 120 行，默认最大字符约 12k。超出时会给 continuation 信息，而不是无限读全文件。

什么时候一定该 get

当问题要求准确日期、决策依据、配置细节、长段上下文、代码/命令原文时，应该在 search 后 get。只问大概偏好或简单事实时，snippet 可能已经够用。

典型调用形态是：

memory_search({
  query: "之前 QMD searchMode 怎么配置"
})

// 假设结果返回：
// path: "memory/2026-05-13.md", startLine: 42, endLine: 58

memory_get({
  path: "memory/2026-05-13.md",
  from: 38,
  lines: 40
})
结论：OpenClaw 的设计是“两步法”：memory_search 找到相关位置，memory_get 再读原文。它有工具能力读相关内容，但不会无条件自动读完整文件；这是为了控制 token、保护边界、降低无关上下文污染。

search 如何映射回原始 Markdown

核心机制是：索引里的每个 chunk 都保留了原始 Markdown 文件坐标。RAG 找到的不是一段“失去来源的向量文本”，而是一条带 path、startLine、endLine 的搜索结果。模型拿到这些字段后，就能构造 memory_get 调用去读原始 Markdown。

sync 阶段读取 MEMORY.md / memory/*.md，生成 file entry：包含绝对路径、相对路径、hash、mtime、size。
chunking 阶段把文件切块，每个 chunk 记录 startLine、endLine、text、hash。
写索引时，builtin 后端把这些坐标写进 chunks 表，也同步写进 chunks_fts 和可选 chunks_vec。
search 阶段无论命中 FTS 还是 vector，SQL 都会取回 path、start_line、end_line、text。
memory_search 输出 JSON，把这些字段交给模型：path、startLine、endLine、snippet、score。
模型如果需要更多上下文，就用这些坐标构造 memory_get({ path, from, lines })。

builtin 后端的数据链路可以简化成：

Markdown file: memory/2026-05-13.md
  line 40..65
    ↓ chunkMarkdown()
chunk {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  text: "...",
  hash: "..."
}
    ↓ writeChunks()
SQLite chunks / chunks_fts / chunks_vec
    ↓ memory_search()
result {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  snippet: "...",
  score: 0.82
}
    ↓ model decides to verify
memory_get({
  path: "memory/2026-05-13.md",
  from: 36,
  lines: 45
})

模型怎么“知道”下一步调 get

工具结果本身给了可读坐标；memory_get 工具描述又说明它是安全读取 memory 文件 excerpt 的工具。所以模型可以把 search result 的 path/startLine/endLine 直接转成 get 参数。

OpenClaw 是否硬编码自动连调

通常不是后端强制自动“search 后立刻 get”。后端负责提供结构化 search 结果和 get 工具。是否继续 get 是模型根据任务判断；但对于需要准确性的回答，正确行为就是 search 后 get。

QMD 怎么映射

QMD 返回 docid / collection / file 等信息。QmdMemoryManager 会把它解析成 doc.rel，如果文件在 workspace 内就返回正常相对路径；如果在 extra collection 里，就返回 qmd/<collection>/... 虚拟路径，保证 search → readFile 能 roundtrip。

为什么不是直接读全文

因为 search result 已经有定位信息，读全文通常浪费 token。更稳的做法是从命中行附近扩展读取，比如 from = startLine - 5、lines = 40。

一句话：索引不是只存 embedding；它还存“这个 embedding 来自哪个 Markdown 文件的哪几行”。RAG 命中后，模型拿到 path + line range，再用 memory_get 回读 Markdown 原文。

分层记忆和会话怎么记住

是的，OpenClaw 实际上是分层记忆。但“跨时间”不只是靠时间戳；时间戳主要用于 daily memory、session 生命周期、排序/衰减和维护。真正让它记住会话的是持久化 session store + JSONL transcript + 可选 session indexing。

第 1 层：当前会话上下文

同一个 session 内，OpenClaw 会持续维护当前对话历史。模型不是每轮从零开始；当前 session 的 transcript / recent context 会参与后续 turn。

第 2 层：session transcript 落盘

会话会写到 ~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl。sessions.json 记录 session 状态和生命周期时间，比如 sessionStartedAt、lastInteractionAt、updatedAt。

第 3 层：durable markdown memory

真正长期、可审计、可编辑的记忆放在 MEMORY.md 和 memory/YYYY-MM-DD.md。这里的日期文件名是跨时间组织记忆的一种方式。

第 4 层：session memory search

如果启用 session indexing，OpenClaw 会把历史 transcript 清洗成 User/Assistant 文本，再作为 source="sessions" 建索引，让 memory_search 能找以前会话里的内容。

会话是这样“被记住”的：

用户消息进入某个 channel，OpenClaw 根据 channel/account/peer/thread 等路由到一个稳定 session。
session store 维护 session id、状态、最近交互时间、启动时间。
每轮用户/助手消息写入对应 <sessionId>.jsonl transcript。
同一 session 后续 turn 可以继续利用当前 transcript / compaction summary / recent tail。
如果启用 session memory search，sync 会扫描 transcript 文件，抽取干净的 User/Assistant 文本，过滤系统包装、heartbeat、cron、silent reply、敏感工具片段等噪音。
这些清洗后的 transcript chunks 被写入 memory index，source 标记为 sessions，之后可以被 memory_search 找到。

builtin session indexing 的配置方向是：

{
  agents: {
    defaults: {
      memorySearch: {
        sources: ["memory", "sessions"]
      }
    }
  },
  experimental: {
    sessionMemory: true
  }
}

QMD 后端的 session indexing 配置方向是：

{
  memory: {
    backend: "qmd",
    qmd: {
      sessions: { enabled: true }
    }
  }
}
关键区别：当前会话靠 session transcript 延续；长期事实靠 Markdown memory 保存；跨会话召回可以靠可选的 session transcript indexing。时间戳帮助排序、生命周期和 daily 文件组织，但不是唯一的“记住机制”。

OpenClaw 是怎么进行工作流编排的

OpenClaw 的工作流编排不是单一模块完成的，而是几层能力叠在一起：触发入口、session/queue、agent loop、tools、background tasks、Task Flow、cron、hooks。简单说：普通对话由 session queue 编排；长期/后台工作由 tasks 和 Task Flow 编排；定时和事件触发由 cron/hooks/webhook 编排。

触发。工作可以来自聊天消息、CLI、cron 定时任务、webhook、内部 hook，或者其他插件。
路由到 session。OpenClaw 根据 channel、account、peer、thread、agentId 等信息找到或创建 session，保证同一条对话线有稳定上下文。
排队。如果当前 session 已有 run 在执行，新消息会进入 queue，按配置决定等待、合并、steer 当前 run，或者作为后续 follow-up。
agent loop 执行。模型读取上下文、形成计划、调用工具、等待工具结果、继续推理，直到生成最终回复或进入后台任务。
工具层执行具体动作。例如 browser、exec、memory、message、sessions、cron、llm-task、lobster 等工具负责实际 I/O。
后台任务。长耗时或 detached work 会落到 background task ledger，便于状态追踪、取消、恢复和审计。
Task Flow 编排多步骤。如果任务是 A→B→C 或有分支、等待、重试、审批，Task Flow 负责 durable flow state、revision tracking，并协调多个 background tasks。
结果交付。最终结果通过 channel send path、message 工具、cron delivery、hook messages 或 task/flow 状态返回给用户。

Session queue 管“同一对话怎么排队”

它解决的是并发问题：同一个 chat/thread 里同时来了多条消息，应该排队、合并、还是插入当前 run。这个层面偏实时对话编排。

Background Tasks 管“后台工作单元”

task 是 detached work 的最小持久记录。它适合单个后台操作，比如跑一次报告、执行一次维护、处理一次长任务。

Task Flow 管“多步骤流程”

Task Flow 在 tasks 之上，管理多步骤、可恢复、有状态的流程。它记录 flow state、revision，并能跨 gateway restart 继续追踪。

Cron / Hooks 管“什么时候触发”

cron 负责定时触发；hooks 负责事件触发，例如 /new、/reset、compaction 前后、gateway startup/shutdown、message received/sent。

一个典型定时工作流可以这样理解：

cron schedule
  -> create/send run into a session
  -> agent loop starts
  -> tool calls / deterministic checks
  -> background tasks for long-running steps
  -> Task Flow tracks A -> B -> C
  -> approval gate if needed
  -> message delivery / task status / flow status
一句话：OpenClaw 的 planning/workflow orchestration 是“session queue 处理实时对话，tasks 记录后台工作，Task Flow 管多步骤状态机，cron/hooks/webhook 负责触发，tools 负责执行”。
参考：docs/automation/taskflow.md、docs/automation/tasks.md、docs/automation/cron-jobs.md、docs/automation/hooks.md、docs/concepts/messages.md、docs/concepts/queue.md、docs/concepts/agent-loop.md

别人问：做一个 agent 系统，怎么设计工作流编排

按照 OpenClaw 的思路，不要把 agent 系统设计成“一个大 while loop 里随便调工具”。更稳的回答是：把工作流拆成触发、会话、队列、执行、工具、后台任务、流程状态、交付、观测这几层。每层职责清楚，系统才可恢复、可审计、可扩展。

可以直接这样回答：我会把 agent 工作流编排设计成分层架构：入口层接收消息/定时/webhook；session 层维护上下文和身份；queue 层处理并发；agent loop 层负责推理和工具调用；tool runtime 层执行外部动作；background task 层承接长任务；flow 层记录多步骤状态机；delivery 层把结果送回用户；observability 层负责日志、状态、取消和恢复。

1. Trigger layer：先统一入口

消息、CLI、cron、webhook、hook、API 请求都先变成统一的 run request。不要让每个入口自己直接驱动模型，否则后面权限、日志、重试会失控。

2. Session layer：上下文必须有归属

每个请求要归到 agent、channel、account、peer/thread、sessionId。这样才能知道该用哪个历史、哪个权限、哪个 workspace、哪个模型配置。

3. Queue layer：并发不要靠运气

同一个 session 同时来多条消息时，要明确策略：排队、合并、steer 当前 run、丢弃、或开新 isolated run。否则 agent 会并发写同一份状态。

4. Agent loop：只负责决策循环

agent loop 做的事是：读上下文 → 计划 → 调工具 → 消化工具结果 → 继续计划 → 输出。它不应该直接承担长期流程状态机和外部调度。

5. Tool runtime：工具是受控 I/O

文件、浏览器、shell、memory、message、sessions、cron、LLM 子任务都应该是有 schema、有权限、有日志的工具，而不是模型自由拼字符串执行。

6. Task / Flow：长流程要持久化

单个后台工作用 task；多个步骤、分支、等待、审批、重试用 flow。flow 里要保存当前 step、状态、revision、子任务 id，保证进程重启后还能恢复。

7. Approval / policy：高风险动作要设门

发消息、改代码、下单、发邮件、执行危险命令这些动作要有 approval gate 或 standing orders，区分“可以自动做”和“必须问人”。

8. Delivery / observability：结果要可追踪

最终输出、进度、失败原因、任务状态、日志、取消信号都要可查。否则用户只会看到 agent 卡住，不知道卡在哪一步。

一个通用 agent workflow 架构可以画成：

input event
  -> normalize request
  -> resolve agent/session/workspace
  -> enqueue or steer
  -> build context
  -> agent loop
      -> tool calls
      -> approvals if needed
      -> background task if long-running
      -> flow state if multi-step
  -> persist transcript/task/flow state
  -> deliver result
  -> emit logs/status/events

如果别人继续问“为什么要这么复杂”，可以回答：

  • 可恢复：进程重启后，task/flow/session 状态还在。
  • 可审计：知道谁触发、做了什么、调用了什么工具、输出到哪里。
  • 可控并发：同一 session 不会多个 agent run 互相踩状态。
  • 可扩展：新增 channel、tool、cron、hook 不需要重写 agent loop。
  • 可治理：高风险动作能被 approval、policy、standing orders 限制。
最短答案：按照 OpenClaw 思路，agent 系统的工作流编排核心不是“让模型自己想办法”，而是把模型放进一个有 session、queue、tool schema、task ledger、flow state、approval 和 delivery 的工程化运行时里。
参考：docs/concepts/messages.md、docs/concepts/queue.md、docs/concepts/agent-loop.md、docs/automation/tasks.md、docs/automation/taskflow.md、docs/automation/cron-jobs.md、docs/automation/hooks.md、docs/concepts/delegate-architecture.md

为什么先 SFT

SFT 先让模型学会固定任务格式：读源码、读 patch、输出完整更新代码。如果没有这个阶段，RL 的 reward 很容易只惩罚错误，却无法稳定教会基本行为。

RLHF 优化什么

GRPO 阶段不是重新定义任务，而是在 SFT 基础上强化四件事：输出可解析、patch 可应用、应用后语法正确、改动规模接近 gold。

数据质量关键点

项目严格过滤提交，并要求生成的 hunk 能唯一匹配和精确还原 after。这样训练数据不是“看起来像 diff”，而是真正可执行、可校验的编辑任务。

当前成熟度

README 明确说 GRPO 先是骨架，真正开训前还要对齐硬件和 reward 细节。因此当前最完整的是数据构建、SFT、生成预测、离线评测链路。

最重要的理解：这个项目训练的不是“会聊天的 Qwen”，而是“能可靠执行代码编辑合并的 Qwen”。SFT 负责学会任务，GRPO/RLHF 负责把输出变得更可解析、更可应用、更正确、更少乱改。

QueryEngine：会话生命周期的外壳

src/QueryEngine.ts 是 headless/SDK 路径的会话生命周期管理器。它持有 mutableMessages、permission denials、usage、read file cache、abort controller、已发现 skills、已加载 nested memory 等状态。每次用户提交消息都会进入 submitMessage()，但这些会话级状态会跨 turn 保留。

输入处理

调用 processUserInput() 解析用户 prompt、slash command、本地命令输出、attachments、memory 触发等，生成要追加到消息流里的 user/system 消息。

Transcript 持久化

用户消息在进入模型循环前就写 transcript，避免进程在 API 返回前被杀导致 --resume 找不到对话。

系统初始化

它会组装 tools、MCP clients、commands、agents、skills、plugins、permission mode、fast mode 等信息，并向 SDK 产出 system init message。

进入核心循环

真正的模型调用与工具循环交给 src/query.ts 的 query()；QueryEngine 负责接收其 yield 的消息、记录 transcript、计算 usage、输出 SDK result。

C3

query()：模型-工具循环怎么跑

src/query.ts 是真正的 agent loop。它不是简单“问一次模型就结束”，而是一个 while (true) 循环：每轮先整理上下文，再调用模型流式输出；如果输出包含 tool_use，就执行工具，把 tool_result 作为 user message 放回上下文，然后继续下一轮。

从上次 compact boundary 后取消息，应用 tool result budget、snip、microcompact、context collapse、auto compact。
拼接 system prompt、user context、system context，选择当前模型和 fallback model。
调用 deps.callModel() 流式收 assistant 消息；发现 tool_use block 时记录到 toolUseBlocks。
如果没有 tool_use，执行 stop hooks、token budget continuation 判断，然后返回 completed。
如果有 tool_use，交给工具编排层执行；工具结果归一化为 user tool_result，追加回下一轮模型上下文。
这就是 Claude Code 的基本“工作流”：模型不是直接改文件，而是反复产生 tool_use，客户端验证权限并执行工具，再把结果喂回模型，直到模型不再请求工具。
C4

工具执行与权限：并发、安全和 hook

工具池由 src/tools.ts 组装：内置工具包括 Agent、Bash、Read/Edit/Write、Glob/Grep、TodoWrite、WebFetch/WebSearch、Skill、Plan、TaskStop、MCP resource 等；feature flag 会条件性加入 Workflow、Sleep、Monitor、Browser、Cron、PushNotification 等工具。

工具池过滤

getTools() 和 assembleToolPool() 会按 permission context、deny rules、MCP tools、simple mode、REPL mode 过滤和去重，决定模型实际能看到哪些工具 schema。

批量并发策略

toolOrchestration.ts 会把连续的 read-only / concurrency-safe 工具并发执行；非并发安全的写操作串行执行，避免多个写工具互相踩状态。

流式工具执行

StreamingToolExecutor 可以在模型流式输出 tool_use 时就开始执行工具；并发安全工具可并跑，非安全工具独占；进度消息会尽快 yield。

权限与 hooks

toolExecution.ts 先做 zod schema 校验、tool.validateInput、PreToolUse hooks、permission decision；允许后才调用 tool.call()，之后再跑 PostToolUse / failure hooks 并生成 tool_result。

assistant tool_use
  -> find tool + schema parse
  -> validateInput
  -> PreToolUse hooks
  -> permission / classifier / user prompt
  -> tool.call(input)
  -> map result to tool_result
  -> PostToolUse hooks
  -> query() receives user tool_result
C5

子代理与后台任务：AgentTool 如何编排

src/tools/AgentTool/AgentTool.tsx 是 Claude Code 子代理系统入口。模型调用 AgentTool 时，可以按 subagent_type 选择 agent definition，也可以指定 model、background、worktree isolation、cwd、team/name 等参数。真正运行子代理的逻辑在 runAgent.ts。

AgentTool 解析输入，检查 agent/team/background/worktree/remote 等约束。
按 agent definition 解析可用工具：内置 agent 可用更多工具，自定义 agent 会过滤危险或不允许的工具；async agent 还有更严格 allowlist。
runAgent() 构造子代理 system prompt、user/system context、MCP servers、frontmatter hooks、skills、独立 transcript。
同步子代理共享父 abort controller；异步/background 子代理使用独立 abort controller，并注册 task state、progress、output file。
子代理内部再次调用同一个 query() loop，因此子代理本身也是完整的模型-工具循环。
关键点：AgentTool 不是特殊魔法；它是“在父会话里启动另一个 query loop”。区别在于子代理有自己的 prompt、tool pool、permission mode、MCP、transcript、progress 和清理逻辑。
C6

Coordinator：多 worker 工作流编排

src/coordinator/coordinatorMode.ts 定义了 Claude Code 的 coordinator 模式。该模式把主 Claude 定位成“协调者”：它不应该把所有事情自己做完，而是把研究、实现、验证拆给多个 worker，并在 worker 结果回来后综合判断下一步。

角色分工

Coordinator 负责理解用户目标、拆任务、写清楚 worker prompt、综合结果并对用户汇报；worker 负责独立研究、实现或验证。

并行优先

源码 prompt 明确鼓励同时发起多个独立 worker：研究任务可以并行，写操作按文件边界避免冲突，验证可以与无冲突实现并行。

通知机制

worker 完成后以 <task-notification> 形式作为 user-role 内部消息回到 coordinator；coordinator 可用 SendMessage 继续同一个 worker，或用 TaskStop 停掉错误方向。

提示词约束

Coordinator prompt 要求每个 worker prompt 自包含：不能说“基于你的发现”，而要由 coordinator 先消化 findings，再给出具体文件、行号、目标和 done 标准。

User asks complex task
  -> Coordinator launches research workers in parallel
  -> workers return task-notification
  -> Coordinator synthesizes concrete spec
  -> continue existing worker or spawn fresh implementation worker
  -> independent verification worker proves behavior
  -> Coordinator reports final state to user
