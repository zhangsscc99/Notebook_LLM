01

memory 的本质是什么

OpenClaw 里的 memory 不是隐藏在模型内部的“神秘长期记忆”。它的本质非常工程化：

把重要信息写到磁盘文件。
把文件切成可检索的 chunks。
建立全文索引与语义索引。
通过 memory_search / memory_get 再把需要的内容取回来。
也就是说：只有真正落盘的东西，才算“被记住”。
参考：docs/concepts/memory.md:9-11
02

memory 里到底存什么

MEMORY.md

长期记忆。适合放稳定偏好、长期决策、持续有效的事实。

memory/YYYY-MM-DD.md

日记式工作层。适合会话摘要、当天观察、上下文碎片。

DREAMS.md

可选。用于 dreaming / promotion / review 相关输出。

extraPaths

配置里可以补充额外可索引目录，让记忆范围超出默认工作区。

搜索一次 memory，大概发生了什么

先检查有没有索引；没有就尝试 sync。
做 query 预处理与 preflight。
如果需要，初始化 embedding provider。
跑 keyword / vector / hybrid 检索。
做 merge、score、filter，然后返回结果。
extensions/memory-core/src/memory/manager.ts
async search(query, opts) {
  if (!hasIndexedContent) await sync(...)
  const preflight = resolveMemorySearchPreflight(...)
  if (preflight.shouldInitializeProvider) await ensureProviderInitialized()
  ... run search ...
}
这就是为什么 memory search 不是“grep 一下文本”——它其实是带索引、带 provider、带 fallback 的完整 retrieval pipeline。

vector search 是怎么做的

如果 sqlite-vec 可用，系统会直接走原生向量 KNN；如果不可用，就退化为读取已保存 embedding，再在进程内做 cosine similarity。

if (await ensureVectorReady(...)) {
  // sqlite-vec native KNN
} else {
  // fallback: parse embeddings + cosineSimilarity
}

所以它不是“没有向量扩展就完全废掉”，而是会优雅降级。

没有索引的时候 sync 是干啥的

在 memory_search 里，如果数据库里还没有任何 chunk，代码会先强制跑一次同步：

if (!hasIndexedContent) {
  await this.sync({ reason: "search", force: true });
}

这里的 sync 不是“同步模型记忆”，而是把磁盘上的 memory 文件整理成可搜索索引。它主要做这些事：

  • 扫描 MEMORY.md、memory/*.md、extra paths，以及可选 session transcript。
  • 读取文件内容，计算 hash、mtime、size，判断哪些文件新增、修改或删除。
  • 把 Markdown 切成 chunks，写入 chunks 表。
  • 更新 FTS 全文索引，让关键词搜索能工作。
  • 如果 embedding provider 可用，就为 chunk 生成 embedding，并写入 vector/embedding 相关存储。
所以第一次搜索前没有索引时，sync 的作用就是“现场建索引”，避免刚启动后第一次搜索直接返回空结果。
参考：extensions/memory-core/src/memory/manager.ts:315-325、extensions/memory-core/src/memory/manager-sync-ops.ts
15

preflight 是什么

preflight 是搜索真正执行前的一道轻量检查。它不查数据库、不调用 embedding provider，只判断这次搜索有没有必要继续。

const normalizedQuery = query.trim();
if (!normalizedQuery) shouldSearch = false;
if (!hasIndexedContent) shouldSearch = false;
otherwise shouldSearch = true and shouldInitializeProvider = true;

在当前实现里，preflight 只做三件事：

  • 把 query 前后空白 trim 掉。
  • 如果 query 为空，就不搜索，也不初始化 provider。
  • 如果没有任何已索引内容，就不搜索，也不初始化 provider。

只有 query 非空且已有索引内容时，它才允许继续搜索，并告诉上层可以初始化 embedding provider。

它的工程价值是避免无意义成本：空 query 或空索引时，不需要启动 embedding provider，也不需要跑 FTS/vector 查询。
参考：extensions/memory-core/src/memory/manager-search-preflight.ts:1-31、extensions/memory-core/src/memory/manager.ts:327-347
16

FTS 虚表是什么

FTS 是 SQLite 的 Full Text Search，全文搜索。所谓“虚表”就是 SQLite 里的 virtual table：它看起来像普通表，可以查询，但底层由扩展模块维护特殊索引结构。

OpenClaw 创建的 FTS 虚表大概长这样：

CREATE VIRTUAL TABLE chunks_fts USING fts5(
  text,
  id UNINDEXED,
  path UNINDEXED,
  source UNINDEXED,
  model UNINDEXED,
  start_line UNINDEXED,
  end_line UNINDEXED
);

这里真正参与全文搜索的是 text。其他字段标成 UNINDEXED，意思是它们只是跟结果一起返回的元数据，不参与倒排索引。

它解决的是关键词搜索问题，比如错误码、配置键、文件名片段、精确术语。vector search 擅长语义相似，但对精确字符串不一定可靠；FTS 则补上这个短板。

所以 hybrid search 里的 “BM25/keyword path” 就依赖 FTS 虚表。它让 memory_search 不只是语义相似搜索，也能找精确词。
参考：packages/memory-host-sdk/src/host/memory-schema.ts:59-82、extensions/memory-core/src/memory/manager-search.ts

memory_get 工具详解

memory_get 的定位不是搜索，而是按路径精确读取一段记忆文件。通常流程是先用 memory_search 找到相关片段，再用 memory_get 拉取更完整、可核对的原文行。

它的参数很少：

  • path：必填，要读取的 memory 文件路径。
  • from：可选，从第几行开始读。
  • lines：可选，读取多少行。
  • corpus：可选，memory、wiki、all。
MemoryGetSchema = {
  path: string,
  from?: number,
  lines?: number,
  corpus?: "memory" | "wiki" | "all"
}

执行时会先解析当前 agent 和配置。如果 memory search 被禁用，工具不会被创建。真正执行时，它按 corpus 和 backend 分支：

  • corpus=wiki：直接去 registered corpus supplement 里读，比如 memory-wiki。
  • builtin backend：调用 readAgentMemoryFile，再进入 readMemoryFile。
  • qmd backend：先拿 MemorySearchManager，再调用它的 readFile。
  • corpus=all：如果 memory 文件读取失败，会尝试从 supplement 里 fallback。

它返回的核心结果是：

{
  path: string,
  text: string,
  from?: number,
  lines?: number,
  truncated?: true,
  nextFrom?: number
}
memory_get 的关键点是“安全精确读取”：它不会全量暴力读取所有 memory，也不会随便读 workspace 里任意文件。
参考：extensions/memory-core/src/tools.ts:391-459、extensions/memory-core/src/tools.shared.ts:38-44、packages/memory-host-sdk/src/host/read-file.ts:48-156
18

每次记忆检索全流程

一次完整的“记忆检索”通常不是单个动作，而是 memory_search 和 memory_get 的组合。

工具可用性检查：memory-core 注册工具时，会确认当前 agent 配置里 memorySearch 没被禁用。
模型先调用 memory_search，传入自然语言 query，例如“之前我们怎么配置 QMD”。
系统拿到 active memory manager。如果 backend 是 QMD，就走 QMD manager；否则走 builtin SQLite manager。
如果索引为空，先强制 sync({ reason: "search", force: true })，把磁盘文件建成可搜索索引。
执行 preflight：空 query 或无索引内容直接停止，避免无意义 provider 初始化和查询。
如果可以搜索，初始化 embedding provider，然后并行/组合执行 FTS keyword search 和 vector search。
把 keyword 和 vector 结果做 hybrid merge，应用 minScore、maxResults、MMR、temporal decay 等策略。
工具返回候选片段，包括 path、startLine、endLine、score、snippet、source。
模型再用 memory_get 按 path/from/lines 读取原文，避免只凭 snippet 回答。

所以实际链路可以理解为：

user question
  -> memory_search(query)
  -> manager.search()
  -> sync if needed
  -> preflight
  -> FTS + vector retrieval
  -> hybrid merge
  -> search results
  -> memory_get(path, from, lines)
  -> exact excerpt
  -> answer with grounded context
RAG 通常对应第 2 到第 8 步；而 OpenClaw 还额外强调第 9 步，也就是用 memory_get 回读原文，降低只看片段摘要造成的误判。
参考：extensions/memory-core/src/tools.ts、extensions/memory-core/src/memory/manager.ts:302-491、packages/memory-host-sdk/src/host/read-file.ts
19

记忆一共有哪些，除了 RAG

如果把 RAG 理解成“搜索索引，然后把相关片段取回上下文”，那 OpenClaw 的 memory 体系里还有几类不是单纯 RAG 的记忆。

Bootstrap Memory

启动新会话时，系统会把 MEMORY.md 和最近几天的 daily memory 以受限预算注入上下文。这不是搜索，而是启动时的基础记忆。

Exact Read Memory

memory_get 按文件和行号读取原文。它不是语义检索，而是精确回读。

Session Memory

可选地把历史 session transcript 建索引，让后续能搜索以前的对话。它属于会话历史召回。

Memory Flush

compaction 前自动提醒模型把重要内容写进 memory/YYYY-MM-DD.md，这是防止上下文压缩丢信息的写入机制。

Dreaming / Promotion

后台整理短期信号，把高价值内容候选提升到长期记忆，并把审阅信息写到 DREAMS.md。

Memory Wiki

memory-wiki 把 durable memory 编译成更像知识库的结构，有 claims、evidence、dashboard、wiki_search、wiki_get。

换句话说，OpenClaw 的记忆不是只有“RAG 搜索”。它至少包括：

  • 启动注入型记忆：直接进入 prompt。
  • 检索型记忆：memory_search。
  • 精确读取型记忆：memory_get。
  • 会话历史型记忆：session transcript indexing。
  • 自动写入型记忆：memory flush。
  • 整理晋升型记忆：dreaming / promotion。
  • 知识库型记忆：memory-wiki。
  • 外部补充语料：registered corpus supplements。
RAG 是 recall 的一部分，但 OpenClaw 的 memory 更像一个“写入、启动注入、搜索、精读、整理、晋升、知识库化”的完整生命周期。
参考：docs/concepts/memory.md、src/auto-reply/reply/startup-context.ts、extensions/memory-core/src/flush-plan.ts、docs/plugins/memory-wiki.md
20

QMD 是什么

QMD 不是 memory 文件本身，也不是某一个 embedding 模型。它是 OpenClaw 可选的本地优先搜索 sidecar / 后端引擎：OpenClaw 把要检索的记忆、额外目录、可选 session transcript 交给 QMD 建 collection，然后通过 qmd search、qmd query 等子进程接口取回结果。

和 builtin 后端的区别

builtin 后端是在 OpenClaw 进程内用 SQLite、FTS、向量索引维护 memory。QMD 后端则把索引更新、BM25 搜索、向量搜索、reranking、query expansion 交给外部 qmd 工具处理。

默认模式不是语义搜索

OpenClaw 的 QMD 默认 searchMode 是 search，也就是 BM25 词法搜索。这个模式下它不会主动维护 semantic embedding。只有 vsearch 或 query 才会进入更语义化的路径。

QMD home 和 collection

启用后，OpenClaw 会在 ~/.openclaw/agents/<agentId>/qmd/ 下管理 QMD home，并从 MEMORY.md、memory/、配置的额外路径、可选 session transcript 创建 collection。

失败时的行为

如果 QMD 不可用、二进制缺失或 sidecar 失败，OpenClaw 会回退到 builtin SQLite memory engine，避免单次 QMD 故障直接让 memory 搜索完全不可用。

启用 QMD 的最小配置类似这样：

{
  memory: {
    backend: "qmd"
  }
}
一句话：QMD 是“把 memory 检索外包给一个更强的本地搜索引擎”。它可以做 BM25、vector search、reranking、query expansion，也可以索引 workspace memory 之外的本地资料。
参考：docs/concepts/memory-qmd.md、packages/memory-host-sdk/src/host/backend-config.ts

embedding 模型用的是啥

这里没有一个全局固定答案，取决于你走的是 builtin memory 后端 还是 QMD 后端，以及配置里的 provider / model 怎么设。

builtin 后端

memory 生命周期全图

OpenClaw memory 的生命周期不是单个“检索函数”，而是一条从写入、建索引、搜索、回读、上下文保全、后台整理组成的链路。

信息先落到可审计的文件或 transcript：MEMORY.md、memory/YYYY-MM-DD.md、可选 session transcript、QMD extra paths。
sync 扫描文件，计算 hash / mtime / size，判断哪些文件新增、变化、删除。
文件被切成 chunk，记录 path、source、startLine、endLine、hash、text。

模型需要旧信息时调用 memory_search 召回候选片段。
如果需要核对原文，再用 memory_get 按 path/from/lines 精确读取。
临近 compaction 时，memory flush 让模型把 durable 信息追加到当天 memory 文件。
dreaming / promotion 后台整理短期信号，产生候选长期记忆或 dream report。

builtin SQLite 表结构

builtin memory index 的核心数据在 SQLite。它不是只存一堆文本，而是把文件状态、chunk、FTS、embedding cache、可选 vector table 分开维护。

meta

存索引元数据，例如 provider/model、chunk 参数、vector 维度、FTS tokenizer、scope hash。用于判断是否需要 full reindex。

files

按 path 记录文件 hash、mtime、size、source。sync 用它判断文件是否变了，以及哪些旧文件已经不存在。

chunks

每个 chunk 一行：id、path、source、start_line、end_line、hash、model、text、embedding、updated_at。它是搜索结果和 memory_get 行号的基础。

chunks_fts / chunks_vec

chunks_fts 是 FTS5 虚表；chunks_vec 是 sqlite-vec 虚表，只有 vector enabled 且扩展可用时创建。

meta
files(path, source, hash, mtime, size)
chunks(id, path, source, start_line, end_line, hash, model, text, embedding, updated_at)
chunks_fts(text, id, path, source, model, start_line, end_line)
chunks_vec(id, embedding)
研究表结构时重点看两件事：source 字段如何区分 memory / sessions，以及 model 字段如何避免不同 embedding 模型的索引混在一起。

chunking 规则

chunking 的目标是把 markdown / transcript 切成适合 embedding 和检索的片段，同时保留原始行号，方便后续 memory_get 回读。

按 token 预算估算字符

chunkMarkdown 根据 chunking.tokens 和内部字符估算上限决定每块大小，不是直接调用 tokenizer 精确切。

支持 overlap

每次 flush 一个 chunk 后，会按 chunking.overlap 保留尾部内容到下一块，减少跨 chunk 信息断裂。

保留 startLine / endLine

每个 chunk 都记录起止行。session transcript 会先转成文本，再用 lineMap 把内容行号 remap 回原 transcript 行。

CJK 长行处理

对中文、日文等 CJK-heavy 长文本，代码会做更细的切分，并避免切断 UTF-16 surrogate pair。

源码核心流程可以简化成：

content.split("\\n")
for each line:
  split long line into segments
  if current chunk exceeds budget:
    flush()
    carryOverlap()
  append segment with lineNo
flush()

FTS + vector 混合排序

builtin search 不是简单“只搜向量”。它优先做 hybrid：关键词 FTS 和向量相似度各自产生候选，然后合并、去重、加权排序。

preflight 清洗 query，并确认索引里有内容。
如果 provider 不可用，就进入 FTS-only 模式，只查 chunks_fts。
如果 provider 可用，先查 FTS 候选，再把 query embed 成向量查 vector 候选。
按 chunk id 合并结果，同一个 chunk 同时保留 vectorScore 和 textScore。
最终分数大致是：vectorWeight * vectorScore + textWeight * textScore。
之后可继续应用 temporal decay 和 MMR，让结果兼顾新近度和多样性。

FTS query 本身会把 query 里的词提取出来，构造成 quoted AND 查询；BM25 rank 会被转成 0 到 1 附近的可合并分数。

研究排序时不要只看 searchVector。真正的排序入口在 mergeHybridResults，还要看 mmr.ts 和 temporal-decay.ts。

memory 写入机制

OpenClaw 的 memory 写入分两类：一类是用户或模型把内容写进 durable memory 文件，另一类是索引器把文件内容写进搜索 index。这两件事不要混在一起。

durable 文件写入

真正长期保留的信息应该追加到 memory/YYYY-MM-DD.md 或维护在 MEMORY.md。memory flush 明确要求 append，不要覆盖。

pre-compaction flush

临近 compaction 时，OpenClaw 可运行 silent memory flush，让模型把本轮值得长期保存的信息写到当天 memory 文件；如果没东西保存则返回 silent token。

索引写入

sync 后 indexFile 会 chunk 文件、生成 embedding、写 chunks、chunks_fts、可选 chunks_vec。

后台整理写入

dreaming / promotion 会记录短期召回信号和 dream report，把可能有价值的信息整理成候选长期记忆。

判断“写 memory”是哪一种：如果写的是 markdown 文件，那是 durable memory；如果写的是 SQLite/QMD，那是检索索引，可以重建。

memory 安全边界

Memory 系统的安全边界主要是：哪些内容会被索引、哪些内容能被工具读、哪些内容会进入 prompt。

索引边界

默认只索引 workspace 的 MEMORY.md 和 memory/，以及配置允许的 extra paths / sessions。watcher 会跳过 .git、node_modules、虚拟环境、缓存目录等。

读取边界

memory_get 不是任意文件读取器。它按受控 memory path、QMD collection prefix 或 registered corpus supplement 读取，并限制行号范围。

session 可见性

session transcript 搜索会经过 filterMemorySearchHitsBySessionVisibility，避免把不该暴露的会话结果直接返回。

失败要显式暴露

embedding quota、provider 错误、FTS/vector 不可用时，工具会返回 disabled/unavailable/debug 信息，调用方不应该假装 memory 搜索成功。

安全上最值得查的不是“能不能搜到”，而是“这个来源是否应该被索引、是否应该被当前 session 看见、是否应该被注入上下文”。

被问 OpenClaw 怎么搞记忆时怎么答

如果别人问“OpenClaw 是怎么搞记忆的”，不要回答成“它有 RAG”这么浅。更准确的回答是：

OpenClaw 的记忆是文件驱动的长期记忆系统。重要信息先写进 MEMORY.md 或 memory/YYYY-MM-DD.md 这类可审计文件，然后 memory-core 或 QMD 把这些文件切成 chunks、建立 FTS/向量索引。模型需要旧信息时先用 memory_search 检索相关片段，再用 memory_get 按路径和行号回读原文。临近 compaction 时还有 memory flush，把当前会话里值得长期保存的信息追加到当天 memory 文件。

你可以按场景用下面三种说法。

30 秒版本

OpenClaw 不是把记忆藏在模型脑子里，而是把记忆显式写成文件。然后它对这些文件建索引，搜索时召回片段，需要核实时再按行读取原文。所以它的 memory 是“文件落盘 + 索引检索 + 原文回读 + compaction 前保全”。

源码版本

工具入口是 memory_search 和 memory_get。它们通过 getMemorySearchManager 拿到 backend manager。builtin 后端是 MemoryIndexManager，用 SQLite、FTS5、可选 sqlite-vec；QMD 后端是 QmdMemoryManager，把检索交给 qmd sidecar。

和普通 RAG 的区别

RAG 只是其中的检索部分。OpenClaw 还包括启动注入、memory flush、session transcript indexing、dreaming / promotion、memory-wiki、registered corpus supplements，以及 memory_get 这种精确原文读取。

一句话判断重点

问“它记住了吗”时，关键不是模型有没有印象，而是信息有没有落盘、有没有被 sync 建索引、搜索结果能不能通过 memory_get 找回原文。

推荐你实际回答时按这个结构：

1. 先说本质：文件驱动，不是模型内部魔法记忆。
2. 再说流程：写文件 -> sync -> chunk -> FTS/vector/QMD index -> memory_search -> memory_get。
3. 再说后端：默认 builtin SQLite/FTS/vector；也可以切到 QMD。
4. 再说扩展：compaction 前 flush，session memory，dreaming，memory-wiki。
5. 最后强调边界：只有落盘并被允许索引/读取的内容，才算可用记忆。
最稳的短答：OpenClaw memory = durable markdown files + searchable index + exact source readback + lifecycle automation。这个答案比单说“RAG”准确得多。

Markdown memory 文件到底干啥

不是。Markdown memory 文件不只是 RAG 之后用来验证全文。它们是 OpenClaw memory 的源数据 / source of truth。RAG index、FTS、vector、QMD collection 都是从这些文件派生出来的缓存或检索结构。

1. 长期记忆的真实载体

MEMORY.md 存 curated long-term memory：稳定事实、偏好、长期决策、短摘要。memory/YYYY-MM-DD.md 存 daily notes：当天上下文、观察、会议/任务记录、较详细的临时知识。

2. 启动上下文来源

MEMORY.md 会作为主长期记忆在主私聊 session 启动时进入上下文，受 bootstrap budget 限制。daily memory 更适合按需检索，避免把所有日志都塞进每次 prompt。

3. 搜索索引的原材料

sync 会扫描这些 Markdown 文件，切成 chunks，写入 SQLite chunks、chunks_fts、可选 chunks_vec；如果用 QMD，就创建/更新 QMD collection。

4. memory_get 的原文来源

memory_search 返回的是片段和行号，memory_get 再按 path/from/lines 回到 Markdown 文件读原文。这确实用于核对 RAG 结果，但只是它的其中一个用途。

5. flush 的写入目标

compaction 前的 memory flush 会要求模型把重要信息追加到 memory/YYYY-MM-DD.md，不是写到向量库本身。向量库之后可以由 sync 重建。

6. 人类可审计和可编辑

因为是普通 Markdown，你可以直接打开、编辑、review、删掉错误记忆。索引只是服务检索；真正该信任和维护的是文件内容。

所以正确关系是：

Markdown memory files
  = durable source of truth
  -> sync/chunk
  -> FTS/vector/QMD index
  -> memory_search returns snippets
  -> memory_get reads original Markdown lines
  -> model answers with verified context
结论：Markdown 文件不是“RAG 后的全文验证附件”。它们是 OpenClaw 记忆的正本。RAG index 是从正本生成的检索视图；memory_get 是回到正本核对和读取更多上下文。

RAG 后会不会读完整相关内容

会，但要说精确一点：OpenClaw 提供了 memory_get 工具让模型在 memory_search 之后读取相关原文；是否调用取决于模型/提示策略和问题是否需要核对。

模型先调用 memory_search(query)。这一步就是 RAG/recall：从 FTS、vector 或 QMD index 里找相关 chunks。
搜索结果会带回 path、startLine、endLine、snippet、score、source/corpus 等信息。
如果 snippet 不够、需要上下文、需要引用原文、或者要避免误读，模型应该继续调用 memory_get(path, from, lines)。
memory_get 回到 Markdown 文件或 QMD collection root，按行读取受限 excerpt。
如果返回 truncated 或 nextFrom，模型可以再次调用 memory_get 继续读后续内容。

不是自动把全文塞进上下文

RAG 搜索不会默认把整个 Markdown 文件全部注入。它先返回相关片段，避免浪费 token。全文或更大范围内容需要通过 memory_get 按需读取。

它知道怎么读，因为工具结果给了坐标

memory_search 的结果包含 path 和行号。模型可以直接把这些坐标传给 memory_get，例如从 startLine 附近多读几十行。

读取也是受限的

memory_get 默认读取有行数和字符预算，默认行数约 120 行，默认最大字符约 12k。超出时会给 continuation 信息，而不是无限读全文件。

什么时候一定该 get

当问题要求准确日期、决策依据、配置细节、长段上下文、代码/命令原文时，应该在 search 后 get。只问大概偏好或简单事实时，snippet 可能已经够用。

典型调用形态是：

memory_search({
  query: "之前 QMD searchMode 怎么配置"
})

// 假设结果返回：
// path: "memory/2026-05-13.md", startLine: 42, endLine: 58

memory_get({
  path: "memory/2026-05-13.md",
  from: 38,
  lines: 40
})
结论：OpenClaw 的设计是“两步法”：memory_search 找到相关位置，memory_get 再读原文。它有工具能力读相关内容，但不会无条件自动读完整文件；这是为了控制 token、保护边界、降低无关上下文污染。

search 如何映射回原始 Markdown

核心机制是：索引里的每个 chunk 都保留了原始 Markdown 文件坐标。RAG 找到的不是一段“失去来源的向量文本”，而是一条带 path、startLine、endLine 的搜索结果。模型拿到这些字段后，就能构造 memory_get 调用去读原始 Markdown。

sync 阶段读取 MEMORY.md / memory/*.md，生成 file entry：包含绝对路径、相对路径、hash、mtime、size。
chunking 阶段把文件切块，每个 chunk 记录 startLine、endLine、text、hash。
写索引时，builtin 后端把这些坐标写进 chunks 表，也同步写进 chunks_fts 和可选 chunks_vec。
search 阶段无论命中 FTS 还是 vector，SQL 都会取回 path、start_line、end_line、text。
memory_search 输出 JSON，把这些字段交给模型：path、startLine、endLine、snippet、score。
模型如果需要更多上下文，就用这些坐标构造 memory_get({ path, from, lines })。

builtin 后端的数据链路可以简化成：

Markdown file: memory/2026-05-13.md
  line 40..65
    ↓ chunkMarkdown()
chunk {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  text: "...",
  hash: "..."
}
    ↓ writeChunks()
SQLite chunks / chunks_fts / chunks_vec
    ↓ memory_search()
result {
  path: "memory/2026-05-13.md",
  startLine: 40,
  endLine: 65,
  snippet: "...",
  score: 0.82
}
    ↓ model decides to verify
memory_get({
  path: "memory/2026-05-13.md",
  from: 36,
  lines: 45
})

模型怎么“知道”下一步调 get

工具结果本身给了可读坐标；memory_get 工具描述又说明它是安全读取 memory 文件 excerpt 的工具。所以模型可以把 search result 的 path/startLine/endLine 直接转成 get 参数。

OpenClaw 是否硬编码自动连调

通常不是后端强制自动“search 后立刻 get”。后端负责提供结构化 search 结果和 get 工具。是否继续 get 是模型根据任务判断；但对于需要准确性的回答，正确行为就是 search 后 get。

QMD 怎么映射

QMD 返回 docid / collection / file 等信息。QmdMemoryManager 会把它解析成 doc.rel，如果文件在 workspace 内就返回正常相对路径；如果在 extra collection 里，就返回 qmd/<collection>/... 虚拟路径，保证 search → readFile 能 roundtrip。

为什么不是直接读全文

因为 search result 已经有定位信息，读全文通常浪费 token。更稳的做法是从命中行附近扩展读取，比如 from = startLine - 5、lines = 40。

一句话：索引不是只存 embedding；它还存“这个 embedding 来自哪个 Markdown 文件的哪几行”。RAG 命中后，模型拿到 path + line range，再用 memory_get 回读 Markdown 原文。

分层记忆和会话怎么记住

是的，OpenClaw 实际上是分层记忆。但“跨时间”不只是靠时间戳；时间戳主要用于 daily memory、session 生命周期、排序/衰减和维护。真正让它记住会话的是持久化 session store + JSONL transcript + 可选 session indexing。

第 1 层：当前会话上下文

同一个 session 内，OpenClaw 会持续维护当前对话历史。模型不是每轮从零开始；当前 session 的 transcript / recent context 会参与后续 turn。

第 2 层：session transcript 落盘

会话会写到 ~/.openclaw/agents/<agentId>/sessions/<sessionId>.jsonl。sessions.json 记录 session 状态和生命周期时间，比如 sessionStartedAt、lastInteractionAt、updatedAt。

第 3 层：durable markdown memory

真正长期、可审计、可编辑的记忆放在 MEMORY.md 和 memory/YYYY-MM-DD.md。这里的日期文件名是跨时间组织记忆的一种方式。

第 4 层：session memory search

如果启用 session indexing，OpenClaw 会把历史 transcript 清洗成 User/Assistant 文本，再作为 source="sessions" 建索引，让 memory_search 能找以前会话里的内容。

会话是这样“被记住”的：

用户消息进入某个 channel，OpenClaw 根据 channel/account/peer/thread 等路由到一个稳定 session。
session store 维护 session id、状态、最近交互时间、启动时间。
每轮用户/助手消息写入对应 <sessionId>.jsonl transcript。
同一 session 后续 turn 可以继续利用当前 transcript / compaction summary / recent tail。
如果启用 session memory search，sync 会扫描 transcript 文件，抽取干净的 User/Assistant 文本，过滤系统包装、heartbeat、cron、silent reply、敏感工具片段等噪音。
这些清洗后的 transcript chunks 被写入 memory index，source 标记为 sessions，之后可以被 memory_search 找到。

builtin session indexing 的配置方向是：

{
  agents: {
    defaults: {
      memorySearch: {
        sources: ["memory", "sessions"]
      }
    }
  },
  experimental: {
    sessionMemory: true
  }
}

QMD 后端的 session indexing 配置方向是：

{
  memory: {
    backend: "qmd",
    qmd: {
      sessions: { enabled: true }
    }
  }
}
关键区别：当前会话靠 session transcript 延续；长期事实靠 Markdown memory 保存；跨会话召回可以靠可选的 session transcript indexing。时间戳帮助排序、生命周期和 daily 文件组织，但不是唯一的“记住机制”。

OpenClaw 是怎么进行工作流编排的

OpenClaw 的工作流编排不是单一模块完成的，而是几层能力叠在一起：触发入口、session/queue、agent loop、tools、background tasks、Task Flow、cron、hooks。简单说：普通对话由 session queue 编排；长期/后台工作由 tasks 和 Task Flow 编排；定时和事件触发由 cron/hooks/webhook 编排。

触发。工作可以来自聊天消息、CLI、cron 定时任务、webhook、内部 hook，或者其他插件。
路由到 session。OpenClaw 根据 channel、account、peer、thread、agentId 等信息找到或创建 session，保证同一条对话线有稳定上下文。
排队。如果当前 session 已有 run 在执行，新消息会进入 queue，按配置决定等待、合并、steer 当前 run，或者作为后续 follow-up。
agent loop 执行。模型读取上下文、形成计划、调用工具、等待工具结果、继续推理，直到生成最终回复或进入后台任务。
工具层执行具体动作。例如 browser、exec、memory、message、sessions、cron、llm-task、lobster 等工具负责实际 I/O。
后台任务。长耗时或 detached work 会落到 background task ledger，便于状态追踪、取消、恢复和审计。
Task Flow 编排多步骤。如果任务是 A→B→C 或有分支、等待、重试、审批，Task Flow 负责 durable flow state、revision tracking，并协调多个 background tasks。
结果交付。最终结果通过 channel send path、message 工具、cron delivery、hook messages 或 task/flow 状态返回给用户。

Session queue 管“同一对话怎么排队”

它解决的是并发问题：同一个 chat/thread 里同时来了多条消息，应该排队、合并、还是插入当前 run。这个层面偏实时对话编排。

Background Tasks 管“后台工作单元”

task 是 detached work 的最小持久记录。它适合单个后台操作，比如跑一次报告、执行一次维护、处理一次长任务。

Task Flow 管“多步骤流程”

Task Flow 在 tasks 之上，管理多步骤、可恢复、有状态的流程。它记录 flow state、revision，并能跨 gateway restart 继续追踪。

Cron / Hooks 管“什么时候触发”

cron 负责定时触发；hooks 负责事件触发，例如 /new、/reset、compaction 前后、gateway startup/shutdown、message received/sent。

一个典型定时工作流可以这样理解：

cron schedule
  -> create/send run into a session
  -> agent loop starts
  -> tool calls / deterministic checks
  -> background tasks for long-running steps
  -> Task Flow tracks A -> B -> C
  -> approval gate if needed
  -> message delivery / task status / flow status
一句话：OpenClaw 的 planning/workflow orchestration 是“session queue 处理实时对话，tasks 记录后台工作，Task Flow 管多步骤状态机，cron/hooks/webhook 负责触发，tools 负责执行”。
参考：docs/automation/taskflow.md、docs/automation/tasks.md、docs/automation/cron-jobs.md、docs/automation/hooks.md、docs/concepts/messages.md、docs/concepts/queue.md、docs/concepts/agent-loop.md

别人问：做一个 agent 系统，怎么设计工作流编排

按照 OpenClaw 的思路，不要把 agent 系统设计成“一个大 while loop 里随便调工具”。更稳的回答是：把工作流拆成触发、会话、队列、执行、工具、后台任务、流程状态、交付、观测这几层。每层职责清楚，系统才可恢复、可审计、可扩展。

可以直接这样回答：我会把 agent 工作流编排设计成分层架构：入口层接收消息/定时/webhook；session 层维护上下文和身份；queue 层处理并发；agent loop 层负责推理和工具调用；tool runtime 层执行外部动作；background task 层承接长任务；flow 层记录多步骤状态机；delivery 层把结果送回用户；observability 层负责日志、状态、取消和恢复。

1. Trigger layer：先统一入口

消息、CLI、cron、webhook、hook、API 请求都先变成统一的 run request。不要让每个入口自己直接驱动模型，否则后面权限、日志、重试会失控。

2. Session layer：上下文必须有归属

每个请求要归到 agent、channel、account、peer/thread、sessionId。这样才能知道该用哪个历史、哪个权限、哪个 workspace、哪个模型配置。

3. Queue layer：并发不要靠运气

同一个 session 同时来多条消息时，要明确策略：排队、合并、steer 当前 run、丢弃、或开新 isolated run。否则 agent 会并发写同一份状态。

4. Agent loop：只负责决策循环

agent loop 做的事是：读上下文 → 计划 → 调工具 → 消化工具结果 → 继续计划 → 输出。它不应该直接承担长期流程状态机和外部调度。

5. Tool runtime：工具是受控 I/O

文件、浏览器、shell、memory、message、sessions、cron、LLM 子任务都应该是有 schema、有权限、有日志的工具，而不是模型自由拼字符串执行。

6. Task / Flow：长流程要持久化

单个后台工作用 task；多个步骤、分支、等待、审批、重试用 flow。flow 里要保存当前 step、状态、revision、子任务 id，保证进程重启后还能恢复。

7. Approval / policy：高风险动作要设门

发消息、改代码、下单、发邮件、执行危险命令这些动作要有 approval gate 或 standing orders，区分“可以自动做”和“必须问人”。

8. Delivery / observability：结果要可追踪

最终输出、进度、失败原因、任务状态、日志、取消信号都要可查。否则用户只会看到 agent 卡住，不知道卡在哪一步。

一个通用 agent workflow 架构可以画成：

input event
  -> normalize request
  -> resolve agent/session/workspace
  -> enqueue or steer
  -> build context
  -> agent loop
      -> tool calls
      -> approvals if needed
      -> background task if long-running
      -> flow state if multi-step
  -> persist transcript/task/flow state
  -> deliver result
  -> emit logs/status/events

如果别人继续问“为什么要这么复杂”，可以回答：

  • 可恢复：进程重启后，task/flow/session 状态还在。
  • 可审计：知道谁触发、做了什么、调用了什么工具、输出到哪里。
  • 可控并发：同一 session 不会多个 agent run 互相踩状态。
  • 可扩展：新增 channel、tool、cron、hook 不需要重写 agent loop。
  • 可治理：高风险动作能被 approval、policy、standing orders 限制。
最短答案：按照 OpenClaw 思路，agent 系统的工作流编排核心不是“让模型自己想办法”，而是把模型放进一个有 session、queue、tool schema、task ledger、flow state、approval 和 delivery 的工程化运行时里。
参考：docs/concepts/messages.md、docs/concepts/queue.md、docs/concepts/agent-loop.md、docs/automation/tasks.md、docs/automation/taskflow.md、docs/automation/cron-jobs.md、docs/automation/hooks.md、docs/concepts/delegate-architecture.md

为什么先 SFT

SFT 先让模型学会固定任务格式：读源码、读 patch、输出完整更新代码。如果没有这个阶段，RL 的 reward 很容易只惩罚错误，却无法稳定教会基本行为。

RLHF 优化什么

GRPO 阶段不是重新定义任务，而是在 SFT 基础上强化四件事：输出可解析、patch 可应用、应用后语法正确、改动规模接近 gold。

Hermes Agent 的 agentic RL：skills 外层 vs 训练内层

按你这个划分，更准确的说法是：

外层不是普通 orchestration，而是agent 应用层面的拟 agentic RL，核心就是 skills 机制；内层才是真正的 agentic RL 训练闭环。
外层 skills 给 agent 一套任务化能力包：专门 prompt、工作流程、工具使用套路、约束、最佳实践。
它会让 agent 看起来越来越像“学会了某种能力”——比如会排查、会研究、会搭建、会编排。
但这层本质上没有 reward 驱动的参数更新，所以它更接近应用层的“拟 agentic RL”或“伪 agentic 强化实践”。
真正的 agentic RL 发生在训练内层：rollout → reward → batch → advantage → loss update → 新 policy → 下一轮 rollout。

外层：skills 机制 = 应用层拟 agentic RL

  • Hermes 的 skills/ 和 optional-skills/ 提供一套可插拔能力包。
  • 每个 skill 本质上是在给 agent 注入任务结构、流程模板、工具套路、领域知识、操作边界。
  • 所以 agent 用了 skill 以后，会表现得像“经过某类任务训练”，但其实主要是prompt/runtime/tooling 层面的行为塑形。
  • 这层很像“应用层强化”：不断把 agent 包装得更会做事，但并没有发生真正的 reward-driven weight update。
  • 因此如果你要叫它外层，最准确就是：skills 是 Hermes 在 agent 应用层做的拟 agentic RL 机制。

内层：真 agentic RL 训练

  • 真正的训练核心在 tinker-atropos 和 Atropos environment。
  • 示例环境 gsm8k_tinker.py 会 collect_trajectories()，一次采多条回答并保留 token / mask / logprob。
  • score() 根据答案正确性给 reward；trainer 再从 /batch 拉回 rollout。
  • pad_data_to_good_offset() 构造 advantage = score - group_mean。
  • train_step() 调 forward_backward_async(..., loss_fn="importance_sampling") 和 optim_step_async，完成真正的参数更新。
  • 更新后的 sampler weights 会立刻进入下一轮 rollout，所以这里存在真实的 policy improvement 闭环。
外层（应用层拟 agentic RL）
  skills
    -> prompt scaffolding
    -> workflow template
    -> tool-use routine
    -> domain-specific operating pattern
    -> 让 agent 看起来更会做事
    -> 但不直接更新模型参数

内层（真正的 agentic RL）
  rollout
    -> reward
    -> batch
    -> advantage = score - group_mean
    -> importance_sampling loss
    -> optimizer step
    -> new sampler weights
    -> next rollout
所以最贴切的总结是：Hermes 的外层 agentic 感主要来自 skills 机制；Hermes 的内层 agentic RL 才来自 Tinker-Atropos / Atropos 这套真正的训练闭环。

H2

skills vs agentic RL：这两者各自优势是什么，agentic RL 能补 skills 什么短板

skills 强在快、便宜、可控、可解释；agentic RL 强在把“会不会做”真正内化到 policy 里。 两者不是互斥关系，更像两层：skills 是应用层行为塑形，agentic RL 是训练层能力塑形。

skills 的优势

  • 上线快：写一个 skill 就能改 agent 行为，不需要重新训练模型。
  • 便宜：主要成本是 prompt、流程和工具设计，不需要大规模 rollout / reward / update。
  • 可控：你可以明确规定步骤、边界、禁区、工具顺序和输出格式。
  • 可解释：agent 为什么这么做，通常能直接从 skill 文本和工具流程里读出来。
  • 适合长尾场景：某个垂类任务、某个平台接入、某个操作手册，优先用 skill 很划算。

skills 的瓶颈

  • 本质仍是外部脚手架：能力更多是“被提示出来”，不是“长进模型里”。
  • 迁移性有限：换一个相邻任务、换一种输入分布，skill 往往要重写或补丁式叠加。
  • 上下文依赖重：很多表现来自 prompt、例子、流程约束，一旦上下文变形，行为会漂。
  • 难以持续自我改进：做完一次任务后，模型参数没变，下次还得靠同样脚手架重新扶着走。
  • 组合复杂度会上升：skill 越多，交叉覆盖、冲突、维护成本会越来越高。

agentic RL 的优势

  • 把行为写进 policy：不是每次提醒模型怎么做，而是通过 reward 和 update 让它逐步学会怎么做。
  • 更适合多步决策：尤其是 rollout 后能看到任务结果、环境反馈、工具后果的场景。
  • 可利用结果信号持续优化：答对/答错、成败、效率、可执行性，都能变成 reward。
  • 能减少对外部脚手架的依赖：学进模型后的能力，理论上更稳，不必事事靠长 prompt 扶着。

agentic RL 能补 skills 哪些短板

  • 补“只会照说明做、不会真正长本事”：skills 像训练手册，RL 才是在训练能力本身。
  • 补“泛化差”：如果 reward 设计得好，模型能学到比单个 skill 更抽象的决策模式。
  • 补“每次都要重新扶”：参数更新后，下一次 rollout 天然带着上一次学到的改进。
  • 补“行为不能闭环优化”：skills 能规定流程，但不能自动根据结果改 policy；RL 可以。
  • 补“复杂多步任务靠 prompt 很脆”：当任务真的是 sequential decision making，RL 比纯 skill 更像正解。
skills
  = runtime scaffolding
  = prompt / workflow / tool routine / guardrails
  = 快、便宜、可控
  = 但能力主要在外面

agentic RL
  = rollout -> reward -> update
  = 能力通过训练写进 policy
  = 慢、贵、复杂
  = 但能持续改进并弥补 skills 的外部脚手架瓶颈
最短总结：skills 解决“先把 agent 做得像会做”；agentic RL 解决“让 agent 真的越来越会做”。

H3

Hermes agentic RL：权重怎么改、LoRA 加哪、训练后怎么变成模型 API

如果把问题收缩到“模型提升原理”，Hermes 这套 agentic RL 的关键不是 skill 文本，而是：在固定底座模型上创建一个 LoRA 训练客户端，让 rollout 的 reward 信号通过 importance sampling loss 回流到 LoRA 参数，再把新权重立刻切到采样端。

先确定底座模型 base_model 和 LoRA rank lora_rank。
通过 Tinker SDK 的 ServiceClient.create_lora_training_client_async(base_model=..., rank=...) 创建 LoRA 训练客户端。
environment 生成 rollout，score 出 reward，Atropos API 聚合成 batch。
trainer 用 forward_backward_async(..., loss_fn="importance_sampling") 和 optim_step_async(...) 更新 LoRA 参数。
训练后通过 save_weights_for_sampler(...) 导出一个新的 sampler 权重路径，再用 create_sampling_client(model_path=...) 切到新模型。
最后用本地 FastAPI 包一层，暴露成 /v1/chat/completions、/v1/completions、/generate 这样的训练后模型 API。

1. 模型权重到底怎么被修改

在这套实现里，不是直接全量更新 base model，而是走 LoRA 训练路径。trainer 初始化时会调用：

self.training_client = await self.service_client.create_lora_training_client_async(
    base_model=self.base_model,
    rank=self.lora_rank,
)

这说明真实被优化的是 LoRA adapter 权重，不是整个底座模型全参。后续每个 step 的更新来自：

await self.training_client.forward_backward_async(data, loss_fn="importance_sampling")
await self.training_client.optim_step_async(adam_params)

也就是说：rollout 先形成训练 datum，loss 回传到 LoRA 参数，再做优化器 step。

2. LoRA 层加在哪里

当前 Hermes / tinker-atropos 这份代码并没有显式展开“LoRA 插到哪几个 projection 层”。它只暴露了两个关键输入：

  • base_model
  • lora_rank

真正把 LoRA adapter 注入到底座模型哪些模块，是由 Tinker 的 LoRA training client 在其内部完成的；这部分在当前仓库里是 SDK / 服务端黑箱，没有像常见 PEFT 配置那样把 q_proj / v_proj / o_proj 明文列出来。

所以准确说法是：Hermes 代码能看到“用了 LoRA + rank 多少”，但看不到“LoRA 精确插在哪些层”；层级注入细节被 Tinker API 抽象掉了。

3. 调用什么 API 做 RL

这里其实有两套 API 在配合：

  • Atropos 本地 API：trainer 会先向 {atropos_api_url}/register 注册，再从 {atropos_api_url}/batch 拉 rollout batch。
  • Tinker SDK API：create_lora_training_client_async、forward_backward_async、optim_step_async、save_weights_for_sampler、create_sampling_client。

所以 RL 不是直接打一条“train()”完事，而是 Atropos 负责环境/rollout，Tinker 负责参数优化和采样客户端。

4. 模型提升原理是什么

提升的核心机制是：对同一问题采多条 rollout，依据 reward 算出组内相对优势：

advantage = score - group_mean

然后只对生成段做训练，把参考 logprob、target token、advantage 一起塞进 datum，交给 Tinker 的 importance_sampling loss。于是模型不是只学“答案对不对”，而是在学：什么样的生成轨迹更值得被提高概率。

这就是 agentic RL 相比 skill 更深的一点：它在改 policy 本身，而不是只在 runtime 外面加操作说明书。

5. 训练后怎么“部署”成可调用模型

这份实现里，训练过程中每一步更新后都会：

new_path = self.training_client.save_weights_for_sampler(name=f"step_{step+1}").result().path
self.current_sampling_client = self.service_client.create_sampling_client(model_path=new_path)

也就是先得到一个新的 model_path（本质上是 Tinker 里的 sampler 权重路径），再创建新的 sampling client。训练结束时还会打印：

tinker://<training_run_id>/sampler_weights/final

这个路径就是训练后模型权重的句柄。

6. 训练好后怎么封装成模型 API

仓库里不是单独写一个“云上部署服务”，而是直接在 trainer 进程里起一个本地 FastAPI 包装层：

  • /v1/completions
  • /v1/chat/completions
  • /generate

这些 endpoint 内部都会调用：

trainer.current_sampling_client.sample_async(...)

因此训练后的模型 API 封装方式就是：把最新的 sampling client 挂到一个 OpenAI-compatible / SGLang-compatible 的本地推理壳上。

base_model + lora_rank
  -> create_lora_training_client_async(...)
  -> rollout batch from Atropos
  -> forward_backward_async(loss_fn="importance_sampling")
  -> optim_step_async(...)
  -> save_weights_for_sampler(...)
  -> create_sampling_client(model_path=new_path)
  -> FastAPI wrapper
      -> /v1/completions
      -> /v1/chat/completions
      -> /generate

如果要把训练后的权重单独导出来，仓库还提供了下载脚本：它通过 create_rest_client() 和 get_checkpoint_archive_url_from_tinker_path(...)，把 tinker://.../sampler_weights/final 下载成归档文件。

最准确的总结是：Hermes 的 agentic RL 不是自己手写 LoRA 注入和底层训练核，而是通过 Tinker 的 LoRA training client 来改 adapter 权重；再把更新后的 sampler client 用 FastAPI 封装成一个训练后模型 API。
参考：/root/hermes/tinker-atropos/tinker_atropos/trainer.py、/root/hermes/tinker-atropos/launch_training.py、/root/hermes/tinker-atropos/tinker_atropos/config.py、/root/hermes/tinker-atropos/tinker_atropos/utils/download_weights.py、/root/hermes/tools/rl_training_tool.py

怎么思考设计 Hermes 的这个工作流：线性顺序说

如果用“怎么设计”来想，Hermes 的工作流不是先想一个大而全的 agent，再往里塞功能；而是按线性运行链倒着设计：用户怎么进来 → 上下文怎么挂上 → 能调用什么 → 模型怎么循环决策 → 长任务怎么拆开 → 结果怎么落盘 → 经验怎么回流。

最顺的设计思路：先把一次 agent run 当成一条流水线，然后逐段问：这一段的输入是什么、状态放哪、失败了怎么恢复、结果给谁看。Hermes 基本就是沿这条顺序长出来的。
先定入口。用户消息、CLI、gateway、cron、webhook 先统一成一个 agent run 请求，不让每个入口自己偷偷驱动一套逻辑。
再定会话归属。每个请求先挂到 session / user / platform / workspace 上，这样后面才知道该用哪份历史、哪套权限、哪个工作目录。
再定运行时能力。根据场景启用对应 toolsets、skills、memory、session search、terminal backend；也就是先决定“这个 agent 这次能干什么”。
再定 prompt 装配。把 system prompt、ephemeral system prompt、skills prompt、memory、session context、用户输入拼起来，形成这次决策的上下文。
再定核心 loop。模型先回答；如果出现 tool_calls，就执行工具，把 tool result 塞回消息，再进下一轮；直到产出最终文本。
再定复杂任务分流。如果任务太长、太并行、太容易阻塞，就交给 delegate/subagent/background task，而不是把所有复杂度都堆进单个同步 loop。
再定持久化。会话消息要写到 SQLite 和 session log，避免中断后什么都丢了；这也是后续 session_search、resume、回顾学习的基础。
最后定闭环学习。一次任务做完后，不只是返回答案，还会把经验回流到 memory、skills、自我回顾里，形成 Hermes 所说的 closed learning loop。

第 1 段：入口统一

设计上第一件事不是模型，而是统一请求入口。Hermes 同时支持 CLI、消息平台、定时任务等，所以要先把这些入口压平成统一 run request；否则后面 session、日志、权限都没法统一。

第 2 段：session 先于智能

Hermes 很强调 session 持久化，因为 agent 的“连续性”不只是模型上下文窗口，而是会话归属、历史消息、标题、平台身份、workspace 状态共同决定的。

第 3 段：工具和 skills 先挂好

真正进入 loop 之前，先根据本次场景挂上可用工具和 skill。这样模型不是裸奔思考，而是在一个带工具、带 guardrails、带工作套路的运行时里决策。

第 4 段：prompt 是装配层

Hermes 的 prompt_builder 做的不是写一段漂亮 system prompt，而是把 memory、session、skills、平台约束、工具能力一起拼装成运行时上下文。

第 5 段：核心 loop 要尽量简单

核心循环最好保持朴素：构建消息 → 调模型 → 执行工具 → 回填结果 → 继续。Hermes 的复杂性主要放在 loop 外围的能力组织，而不是把 loop 本身写成一团巨型状态机。

第 6 段：复杂度外溢到子代理

当一个任务天然可并行、耗时长、或需要隔离上下文时，就交给 delegate_tool / subagent。这样主 loop 仍保持线性，但系统整体又能支持复杂编排。

第 7 段：结果必须落盘

Hermes 把 session 写入 SQLite 和 JSON log，不只是为了调试，而是因为没有持久化，就没有 resume、session_search、跨会话学习和审计。

第 8 段：把一次任务变成下次能力

这是 Hermes 跟普通 agent 最大的设计差别之一：任务结束后还会思考要不要更新 skill、要不要写 memory、要不要形成下一次可复用的经验。

input event
  -> resolve session / platform / workspace
  -> enable toolsets + skills + memory
  -> build runtime prompt/context
  -> model call
  -> if tool_calls: run tools and loop
  -> if task too complex: delegate / background task
  -> final response
  -> persist session/logs/state
  -> memory / skill / review feedback loop
所以线性顺序地说，Hermes 这套工作流的设计思想就是：先把运行时骨架搭稳，再让模型在这个骨架里循环决策，最后把每次任务沉淀成下次能力。
参考：/root/hermes/CONTRIBUTING.md（Architecture Overview / Core Loop）、/root/hermes/run_agent.py、/root/hermes/agent/prompt_builder.py、/root/hermes/tools/delegate_tool.py、/root/hermes/README.md
HW2

如果用 LangGraph / LangChain 重新设计 Hermes 工作流编排

如果用 LangGraph 来重做 Hermes，我不会先追求“一个超智能 agent”，而会先把 Hermes 现在已经有的运行时拆成图里的几个稳定节点，再用条件路由把它们串起来。最自然的思路是：session / context / model loop / tools / delegate / approval / persistence / learning review 分层建图。

核心原则：用 StateGraph 管 Hermes 的状态流；用 ToolNode 管工具执行；用 Command 或 add_conditional_edges() 做动态路由；用 checkpointer + thread_id 做 session 持久化；用 interrupt() 处理审批和人类介入。
先定义 graph state。用 MessagesState 或自定义 TypedDict / Pydantic state，至少放：messages、session metadata、enabled toolsets、skills、memory hits、todo/task state、delegate requests、review flags。
再搭主图骨架。用 StateGraph(...)，从 START 进入 ingress/session 节点，最后落到 END。
把 prompt 装配做成节点。不要把 prompt_builder 散在各处，而是单独一个 node：收集 memory、skills、session context，再产出给模型调用的 messages。
把模型思考和工具执行拆开。一个 llm node 只负责产出 assistant message / tool calls；一个 ToolNode 负责真正执行工具。
用动态路由驱动循环。如果模型输出 tool calls，就 route 到 tools；如果要 delegate，就 route 到 subgraph；如果无 tool calls，就 route 到 final response。
把复杂能力拆成 subgraphs。delegate、多 worker、后台任务、skill review 都不要塞进主 loop，而是做成 compiled subgraph 再挂回主图。
给高风险节点加 interrupt。文件写入、危险命令、外发消息、人工审批，统一通过 interrupt() 停住，等人类用 Command(resume=...) 恢复。
最后加 persistence 和 learning loop。编译时挂 InMemorySaver / PostgresSaver，执行时带 thread_id；任务结束后再进 skill/memory review 节点，把经验沉淀回系统。

1. 图的根骨架怎么搭

from langgraph.graph import StateGraph, START, END
from langgraph.graph import MessagesState

builder = StateGraph(MessagesState)
builder.add_node("ingress", ingress_node)
builder.add_node("assemble_context", assemble_context_node)
builder.add_node("llm", llm_node)
builder.add_node("tools", tool_node)
builder.add_edge(START, "ingress")

这里最像 Hermes 的，是先把“收到请求”“装配上下文”“模型决策”“工具执行”拆成显式节点，而不是把一切塞进一个大函数。

2. Hermes 的 session 怎么映射

Hermes 很强调 session，所以 LangGraph 版本里一定要把 session 放到 persistence 层，而不是只靠 messages 列表。直接做法是：

  • 编译图时加 checkpointer=InMemorySaver()（开发）或 PostgresSaver（生产）
  • 每次调用图时传 config={"configurable": {"thread_id": ...}}

这样 Hermes 的 session resume / thread continuity 就可以直接映射到 LangGraph 的 thread/checkpoint 模型。

3. prompt_builder 怎么落到 LangChain

Hermes 现在有很重的 prompt 装配层。如果换 LangChain，我会把这层拆成：

  • ChatPromptTemplate.from_messages(...)
  • MessagesPlaceholder 放历史消息
  • 一个 context assembly node 在调用模型前，把 memory / skills / platform constraints 组进 prompt variables

也就是说，prompt 不是静态字符串，而是“LangChain prompt object + LangGraph context node”联合生成。

4. 工具循环怎么设计

Hermes 的核心就是 tool loop。LangGraph 版最自然的写法是：

  • 工具定义用 @tool
  • 执行器用 langgraph.prebuilt.ToolNode
  • llm node 产出 tool calls 后，通过 add_conditional_edges() 或 Command(goto="tools") 跳到 tools node
  • tools node 执行完成，再回到 llm node 继续循环
builder.add_conditional_edges(
    "llm",
    route_after_llm,
    {"tools": "tools", "delegate": "delegate", "final": "finalize"}
)

5. delegate / subagent 怎么映射

Hermes 的 delegate_tool 很重。如果用 LangGraph，我会把 delegate 做成单独 subgraph，而不是普通工具文本返回：

  • 父图用 builder.add_node("delegate", compiled_subgraph)
  • subgraph 里再处理 child context、child tools、child result merge
  • 如果需要 fan-out，可用 Send 从条件边批量派发多个并行任务

这样比把 delegate 完全伪装成单个 tool call 更清晰，也更贴近 Hermes 的真实结构。

6. 审批和危险操作怎么做

Hermes 现在有 approval 思路。LangGraph 版最标准的是在关键节点直接调用 interrupt()，把图暂停；等人类确认后，用 Command(resume=...) 恢复执行。

这很适合映射：

  • 危险 shell 命令
  • 文件写入
  • 外发消息
  • 高风险自动操作

7. learning loop 怎么接回去

Hermes 的特色不是只输出答案，而是会做 skill review / memory 回流。所以图跑到 final response 后，我会再挂一个 post-run review node：

  • 读本次 messages / tool traces
  • 判断要不要更新 memory
  • 判断要不要新建或修改 skill
  • 把结果写入 store / filesystem

如果想和 LangChain store 体系对齐，可以在 runtime context 里接持久化 store；短期记忆靠 checkpointer，长期记忆靠 store。

8. 为什么不用 create_agent 一把梭

LangChain 的 create_agent 更适合快速起一个标准 agent；但 Hermes 这种“session 很重、tool loop 很重、delegate 很重、learning loop 很重”的系统，更适合直接用 LangGraph 原生 Graph API 自己搭。原因是：

  • 你能显式控制节点边界
  • 你能显式控制状态结构
  • 你能显式控制审批、持久化、并行、子图
  • 你能让系统结构更接近 Hermes 真实运行时，而不是被通用 agent abstraction 压扁
LangGraph 版 Hermes（推荐骨架）
START
  -> ingress/session_resolve
  -> assemble_context
  -> llm
      -> conditional route
         -> tools (ToolNode) -> llm
         -> delegate_subgraph -> llm
         -> approval_interrupt -> resume -> llm
         -> finalize
  -> post_run_review
      -> memory update
      -> skill update
  -> END
如果一句话总结：用 LangGraph 重做 Hermes，关键不是“把 agent 跑起来”，而是把 Hermes 已有的 session、tool loop、delegate、approval、learning review 全都提升为图上的一等公民。

HS1

概览：Hermes Agent 里面是不是有沙箱

有。Hermes 里的“沙箱”不是单一一种东西，而是分成几层：终端执行沙箱、代码执行沙箱、文件工具跨后端沙箱适配、以及浏览器运行时的 sandbox 处理。最重要的是前两类。

一句话：Hermes 的沙箱核心在 terminal backend。命令可以跑在 local，也可以跑在 Docker、Singularity、Modal、Daytona、Vercel Sandbox、SSH 这些隔离或远程环境里；execute_code 又在这个基础上再包一层 Python 脚本沙箱和工具 RPC。
先选 backend。terminal_tool.py 支持 local、docker、singularity、modal、daytona、vercel_sandbox、ssh。
再创建执行环境。非 local 后端会创建容器、云沙箱或远端执行环境；Hermes 用 task_id / sandbox key 把一次任务和对应环境关联起来。
终端和文件工具走同一后端。file tools 不是只读本机文件，而是通过 terminal backend 的 execute 接口适配 Docker、Modal、Daytona 等环境。
execute_code 再包一层。它把用户 Python 代码放进临时 sandbox 目录，生成受限的 hermes_tools.py，只允许调用白名单工具，并过滤 secrets。
长期任务也按沙箱记录。process_registry 会区分 host PID 和 sandbox PID；非 local 后端会在沙箱内部启动、轮询、停止任务。
浏览器是另一类隔离。browser_tool 会在某些环境下注入 --no-sandbox 等 Chromium 参数，这是浏览器进程自己的 sandbox 兼容处理，不等同于 terminal sandbox。

1. 终端沙箱：Hermes 最核心的隔离层

tools/terminal_tool.py 明确把执行后端抽象成多种环境：local 是本机直跑；Docker / Singularity 是容器；Modal / Daytona / Vercel Sandbox 是云端沙箱；SSH 是远端机器。README 也把这些称为 terminal backends。

所以问“有没有沙箱”，答案是：有，但取决于你配置的 terminal backend。如果 backend 是 local，那命令就在本机跑；如果是 Docker / Modal / Daytona / Vercel，就进入隔离环境。

2. 配置层：不是默认全都隔离

cli-config.yaml.example 里有 terminal backend 配置示例。比如 Docker 后端可以显式设置 image、volume、是否把当前目录 mount 到 /workspace；这个 mount 选项默认关闭，因为它会把宿主工作目录暴露给容器。

这点很关键：Hermes 支持沙箱，但不是说所有操作天然都在安全容器里。安全边界来自 backend 选择和配置。

3. execute_code：Python 子进程沙箱

tools/code_execution_tool.py 是另一层。它会创建临时目录，例如 hermes_sandbox_* 或远端 hermes_exec_*，把脚本和受限 RPC 工具模块放进去执行。

这个沙箱还会限制可调用工具集合，只暴露白名单里的工具，并且对环境变量和输出做 secret redaction，避免脚本直接读到 API key、token 等敏感信息。

4. 文件工具跟着后端走

tools/file_operations.py 的设计是跨 terminal backend 工作。也就是说，如果 terminal backend 是 Docker 或 Modal，文件读写/search/patch 等也应该作用在那个环境里，而不是误读宿主机路径。

这就是 Hermes 设计里的一个重要点：terminal、file、background process 尽量共享同一个执行环境语义。

5. 后台任务也有沙箱意识

tools/process_registry.py 会记录进程是在 host 还是 sandbox 里。对 Docker、Modal、Daytona、SSH 这类非 local 后端，它会在沙箱内部启动命令、记录沙箱内 PID，并通过后续 execute 调用轮询日志或停止进程。

6. RL / benchmark 里也会用隔离沙箱

environments/hermes_base_env.py 和 terminal test env 里能看到，RL rollout 或 benchmark 会给每个任务配置 terminal backend，例如 Modal 云沙箱。这样不同 rollout 不共享同一个本机执行环境。

Hermes sandbox layers
  terminal backend
    -> local / docker / singularity / modal / daytona / vercel_sandbox / ssh
  file operations
    -> execute through the active terminal backend
  execute_code
    -> temporary script sandbox
    -> restricted hermes_tools.py RPC
    -> secret stripping / output redaction
  background tasks
    -> host PID or sandbox PID tracking
  browser runtime
    -> Chromium sandbox compatibility flags when needed
最短答案：Hermes 有沙箱能力，但它是后端驱动的。真正隔离强弱取决于 terminal backend；execute_code 在此基础上再做一层 Python 执行沙箱。

沙箱原理：edit_file / 多文件项目到底怎么改

理解 Hermes 沙箱时，最容易误解的一点是：它不是永远把整个项目复制进沙箱，改完再整体拷回来。更准确地说，Hermes 有一个统一的 file / terminal 抽象，真正文件在哪里被改，取决于当前 terminal backend。

最短答案：本地 backend 是直接改宿主项目；Docker/Singularity 如果 bind mount 了项目，就是在容器里改挂载目录，实际立刻落到宿主文件；Modal/Daytona 这类云沙箱默认主要同步 ~/.hermes 状态，不会自动把任意大项目整包同步来回，除非你在沙箱里 clone / 上传 / 挂载 / 自己做同步。
先确定当前 backend。Hermes 看配置里的 terminal.backend，决定文件工具和终端命令运行在哪里。
file tools 不自己发明一套文件系统。read_file、write_file、patch、search 会通过当前 backend 的执行环境理解路径。
local 模式。路径就是宿主机路径，改 /root/project/a.py 就是直接改这台机器上的文件。
Docker bind mount 模式。如果 docker_mount_cwd_to_workspace: true，宿主项目被挂到容器 /workspace；容器内改 /workspace/a.py，宿主项目马上变化，不需要 copy back。
云沙箱模式。Modal / Daytona 会创建远端沙箱；代码在沙箱内执行。默认同步的是 Hermes 自己的运行状态目录，不等于自动同步整个用户项目。
execute_code 模式。Python 代码先被放进临时 sandbox 目录运行；如果它要改项目文件，通常还是通过 Hermes 暴露的文件工具 RPC 去改当前 backend 里的项目。

案例 1：local 后端改很多文件

假设项目在 /root/myapp，Hermes 当前 terminal backend 是 local，cwd 也是这个项目。

terminal.backend = local
cwd = /root/myapp

patch src/a.py
write_file src/b.py
search src/
run pytest

这时没有“复制到沙箱”这一步。Hermes 的 file tool 直接改宿主机上的 /root/myapp/src/a.py、/root/myapp/src/b.py。跑测试也是在宿主机项目里跑。

案例 2：Docker 后端改宿主项目

如果你启用 Docker，并显式打开：

terminal:
  backend: "docker"
  cwd: "/workspace"
  docker_mount_cwd_to_workspace: true

Hermes 会让容器看到宿主启动目录的内容。此时 agent 在容器里看到的是 /workspace，但这个目录背后是宿主项目的 bind mount。

所以 Docker 这种情况下不是“先复制，再拷回”；更像是“容器拿着宿主项目目录的一个挂载视图在改”。

案例 3：Docker 不挂载项目

如果 docker_mount_cwd_to_workspace 是 false，容器默认看不到宿主当前项目。你在容器里改的文件只是容器文件系统里的文件。

这种模式隔离更强，但也意味着：如果你想让改动回到宿主项目，需要额外的同步、复制、git push，或者一开始就把项目 clone 到容器里并从容器提交。

案例 4：Modal / Daytona 云沙箱

Modal / Daytona 的 backend 会创建远端沙箱，并在执行前后通过 FileSyncManager 同步文件。但从代码看，默认同步重点是 ~/.hermes 这类 Hermes 状态目录，不是任意项目源码树。

所以如果你说“一个具体项目，要改很多文件”，云沙箱里通常有三种做法：在沙箱里 git clone 项目后改并 push；显式上传需要的项目文件；或者配置持久沙箱 / 快照让项目留在沙箱里。

案例 5：execute_code 不是项目复制器

execute_code 会创建临时目录，把用户 Python 脚本和受限 hermes_tools.py 放进去运行。这层主要是为了限制 Python 脚本能调用什么工具、能看到什么环境变量。

如果脚本里调用文件工具去改项目，最终还是回到“当前 terminal backend 的项目在哪里”这个问题。它本身不是把整个项目复制进去改完再还原的机制。

怎么判断自己属于哪一种

看三件事就够了：

  • terminal.backend 是 local、docker、modal、daytona 还是 ssh。
  • 当前 cwd 是宿主路径、容器路径，还是远端路径。
  • 有没有 mount / clone / sync 配置把项目放进那个环境。

这三件事决定 editfile 是直接改宿主、通过挂载改宿主，还是只改沙箱内部文件。

edit_file / patch mental model

local backend
  -> edit host project directly

docker with cwd bind mount
  -> edit /workspace in container
  -> host project changes immediately through mount

docker without mount
  -> edit container filesystem only
  -> need explicit copy / git push / sync to get changes out

modal / daytona
  -> edit remote sandbox filesystem
  -> default sync is mainly Hermes state
  -> project source must be cloned, mounted, uploaded, or otherwise synced

execute_code
  -> run script in temp sandbox
  -> file changes happen through allowed Hermes tools and active backend
所以你问“是不是把项目直接复制到沙箱里去改，再把文件拷回来”：不一定，而且通常不是这么简单粗暴。Hermes 的核心是统一 backend 抽象；项目文件是否复制、挂载、同步，要看 backend 和配置。

沙箱有哪些亮点功能，有什么意义

Hermes 沙箱的亮点不只是“能开一个 Docker”。它真正有价值的地方，是把 agent 的命令执行、文件读写、后台进程、Python 脚本、RL rollout 放到同一个 backend 抽象下面。这样 agent 不是只能在你电脑上裸跑，而是可以按任务选择本地、容器、远端云沙箱或 SSH 机器。

一句话：Hermes 沙箱的意义是把“不可信、会改文件、会跑命令、会装依赖、会启动服务”的 agent 行为，变成可隔离、可复现、可迁移、可并行、可训练的数据生产流程。

亮点 1：七类 terminal backend，不锁死在本机

Hermes 支持 local、Docker、SSH、Singularity、Modal、Daytona、Vercel Sandbox。这个设计比“只支持本机 shell”强很多：轻任务可以 local 直跑；危险任务可以进 Docker；需要云端长期环境可以用 Modal / Daytona；需要 GPU 或公司内网资源可以走 SSH / Singularity。

意义：agent 的运行位置可以按任务切换。它不是一个固定 IDE 插件，而是一个可以搬到 VPS、云沙箱、GPU 集群、远端服务器上的执行系统。

亮点 2：terminal、file、process 共享同一个执行环境

很多 agent 框架的问题是：命令在容器里跑，文件工具却还在宿主机读写，最后路径语义乱掉。Hermes 的思路是让文件操作、终端命令、后台进程都尽量跟随 active terminal backend。

意义：如果 agent 在 Docker 的 /workspace 跑测试，它 patch 的也应该是同一个 /workspace 里的代码；这样“看到的文件”和“执行的代码”一致，工程任务不容易跑偏。

亮点 3：Docker bind mount 是显式 opt-in

docker_mount_cwd_to_workspace 默认关闭。也就是说 Hermes 不会默认把你启动目录暴露给容器；你要让容器直接改宿主项目，需要明确打开挂载。

意义：这是一个安全边界。默认更保守，需要真实改项目时再主动授权；否则 agent 在容器里乱写，影响范围主要留在容器文件系统里。

亮点 4：云沙箱支持持久环境和低成本休眠

README 里强调 Modal / Daytona 可以提供 serverless persistence：环境空闲时休眠，需要时再唤醒。代码层面也区分 persistent filesystem 和 live sandbox / long-running process。

意义：这让 agent 可以做长周期任务：今天装依赖、clone 项目、跑一半，明天继续；同时不必一直占着一台昂贵机器。

亮点 5：execute_code 有工具白名单和输出脱敏

execute_code 会生成受限的 hermes_tools.py，脚本只能调用允许的 Hermes 工具；输出还会做 secret redaction，避免 API key、token 等敏感信息进入模型上下文。

意义：这不是普通的“让模型写段 Python 随便跑”。它把多步工具调用封装成可控脚本：能循环、能过滤大输出、能批处理，同时降低越权和泄密风险。

亮点 6：后台任务有 sandbox PID 记录

Hermes 的 process registry 会区分 host PID 和 sandbox PID。非 local 后端里启动的服务、测试、长进程，需要在对应沙箱内部轮询、停止、清理。

意义：agent 可以启动 dev server、训练脚本、benchmark，然后后续继续查日志或停止它；不会只得到一个脱离上下文的本机进程号。

亮点 7：RL / benchmark 可以按 task_id 隔离环境

Hermes 的 terminal 环境里有 per-task override 机制。普通子 agent 可以共享父任务容器；但 RL rollout / benchmark 可以注册自己的 task_id、镜像、cwd，从而拿到独立沙箱。

意义：这对 agentic RL 很关键。训练数据必须避免不同 rollout 互相污染，否则 reward、轨迹、文件状态都不干净。独立沙箱让每条训练轨迹更像真实独立任务。

亮点 8：资源限制和镜像配置可控

容器 / 云沙箱 backend 可以配置 CPU、memory、disk、image、cwd、persistent 等。RL 或 SWE benchmark 还能针对任务覆盖镜像。

意义：同一个 agent 可以跑不同强度的任务：普通脚本给小资源；编译大型项目给更大磁盘；GPU / 特定依赖用定制镜像。这是工程化 agent 必须要有的调度能力。

安全意义。把危险命令、依赖安装、未知代码运行限制在容器或远端沙箱里，减少对宿主机的破坏面。
工程意义。让 agent 的文件、命令、进程路径一致，减少“文件在 A 环境改、测试在 B 环境跑”的错位。
产品意义。用户可以从 Telegram / Slack / CLI 远程发任务，agent 在云沙箱里继续工作，不依赖用户电脑一直开着。
训练意义。RL rollout 可以隔离、并行、复现；每条轨迹都有干净环境，更适合做 agentic RL 数据。
成本意义。云沙箱可以休眠，空闲时少花钱；需要算力时再唤醒或换资源规格。
扩展意义。backend 抽象做好后，未来新增一个执行环境，不必重写所有 file / terminal / process 逻辑。
Why Hermes sandbox matters

without sandbox abstraction
  -> model issues commands on one machine
  -> files may be edited in another place
  -> long tasks are hard to track
  -> RL rollouts contaminate each other
  -> unsafe code can damage host directly

with Hermes backend abstraction
  -> choose local / docker / modal / daytona / ssh per task
  -> terminal + file + process share environment semantics
  -> execute_code uses allowed tool RPC + secret redaction
  -> benchmarks and RL can get isolated task sandboxes
  -> cloud environments can persist or hibernate
最终价值：沙箱让 Hermes 从“会调用工具的聊天机器人”升级成“能安全执行真实工程任务的 agent runtime”。没有这层，agentic RL 训练、SWE benchmark、多文件代码修改、远程长期任务都会非常脆弱。

QueryEngine：会话生命周期的外壳

src/QueryEngine.ts 是 headless/SDK 路径的会话生命周期管理器。它持有 mutableMessages、permission denials、usage、read file cache、abort controller、已发现 skills、已加载 nested memory 等状态。每次用户提交消息都会进入 submitMessage()，但这些会话级状态会跨 turn 保留。

输入处理

调用 processUserInput() 解析用户 prompt、slash command、本地命令输出、attachments、memory 触发等，生成要追加到消息流里的 user/system 消息。

Transcript 持久化

用户消息在进入模型循环前就写 transcript，避免进程在 API 返回前被杀导致 --resume 找不到对话。

系统初始化

它会组装 tools、MCP clients、commands、agents、skills、plugins、permission mode、fast mode 等信息，并向 SDK 产出 system init message。

进入核心循环

真正的模型调用与工具循环交给 src/query.ts 的 query()；QueryEngine 负责接收其 yield 的消息、记录 transcript、计算 usage、输出 SDK result。

C3

query()：模型-工具循环怎么跑

src/query.ts 是真正的 agent loop。它不是简单“问一次模型就结束”，而是一个 while (true) 循环：每轮先整理上下文，再调用模型流式输出；如果输出包含 tool_use，就执行工具，把 tool_result 作为 user message 放回上下文，然后继续下一轮。

从上次 compact boundary 后取消息，应用 tool result budget、snip、microcompact、context collapse、auto compact。
拼接 system prompt、user context、system context，选择当前模型和 fallback model。
调用 deps.callModel() 流式收 assistant 消息；发现 tool_use block 时记录到 toolUseBlocks。
如果没有 tool_use，执行 stop hooks、token budget continuation 判断，然后返回 completed。
如果有 tool_use，交给工具编排层执行；工具结果归一化为 user tool_result，追加回下一轮模型上下文。
这就是 Claude Code 的基本“工作流”：模型不是直接改文件，而是反复产生 tool_use，客户端验证权限并执行工具，再把结果喂回模型，直到模型不再请求工具。
C4

工具执行与权限：并发、安全和 hook

工具池由 src/tools.ts 组装：内置工具包括 Agent、Bash、Read/Edit/Write、Glob/Grep、TodoWrite、WebFetch/WebSearch、Skill、Plan、TaskStop、MCP resource 等；feature flag 会条件性加入 Workflow、Sleep、Monitor、Browser、Cron、PushNotification 等工具。

工具池过滤

getTools() 和 assembleToolPool() 会按 permission context、deny rules、MCP tools、simple mode、REPL mode 过滤和去重，决定模型实际能看到哪些工具 schema。

批量并发策略

toolOrchestration.ts 会把连续的 read-only / concurrency-safe 工具并发执行；非并发安全的写操作串行执行，避免多个写工具互相踩状态。

流式工具执行

StreamingToolExecutor 可以在模型流式输出 tool_use 时就开始执行工具；并发安全工具可并跑，非安全工具独占；进度消息会尽快 yield。

权限与 hooks

toolExecution.ts 先做 zod schema 校验、tool.validateInput、PreToolUse hooks、permission decision；允许后才调用 tool.call()，之后再跑 PostToolUse / failure hooks 并生成 tool_result。

assistant tool_use

  -> validateInput
  -> PreToolUse hooks
  -> permission / classifier / user prompt
  -> tool.call(input)
  -> map result to tool_result
  -> PostToolUse hooks
  -> query() receives user tool_result

子代理与后台任务：AgentTool 如何编排

src/tools/AgentTool/AgentTool.tsx 是 Claude Code 子代理系统入口。模型调用 AgentTool 时，可以按 subagent_type 选择 agent definition，也可以指定 model、background、worktree isolation、cwd、team/name 等参数。真正运行子代理的逻辑在 runAgent.ts。

AgentTool 解析输入，检查 agent/team/background/worktree/remote 等约束。
按 agent definition 解析可用工具：内置 agent 可用更多工具，自定义 agent 会过滤危险或不允许的工具；async agent 还有更严格 allowlist。
runAgent() 构造子代理 system prompt、user/system context、MCP servers、frontmatter hooks、skills、独立 transcript。
同步子代理共享父 abort controller；异步/background 子代理使用独立 abort controller，并注册 task state、progress、output file。
子代理内部再次调用同一个 query() loop，因此子代理本身也是完整的模型-工具循环。
关键点：AgentTool 不是特殊魔法；它是“在父会话里启动另一个 query loop”。区别在于子代理有自己的 prompt、tool pool、permission mode、MCP、transcript、progress 和清理逻辑。
C6

Coordinator：多 worker 工作流编排

src/coordinator/coordinatorMode.ts 定义了 Claude Code 的 coordinator 模式。该模式把主 Claude 定位成“协调者”：它不应该把所有事情自己做完，而是把研究、实现、验证拆给多个 worker，并在 worker 结果回来后综合判断下一步。

角色分工

Coordinator 负责理解用户目标、拆任务、写清楚 worker prompt、综合结果并对用户汇报；worker 负责独立研究、实现或验证。

并行优先

源码 prompt 明确鼓励同时发起多个独立 worker：研究任务可以并行，写操作按文件边界避免冲突，验证可以与无冲突实现并行。

通知机制

worker 完成后以 <task-notification> 形式作为 user-role 内部消息回到 coordinator；coordinator 可用 SendMessage 继续同一个 worker，或用 TaskStop 停掉错误方向。

提示词约束

怎么用 LangGraph 实现类似 Claude Code 的工作流编排

如果用 LangGraph 复刻 Claude Code 的工作流，不要把它设计成“一个大 agent prompt”。更稳的设计是把 Claude Code 里的隐式循环显式拆成一张有状态图：主会话状态、模型决策节点、工具执行节点、权限/hook 节点、子代理调度节点、压缩/恢复节点、最终汇总节点。

核心映射：Claude Code 的 QueryEngine + query loop + tool orchestration + AgentTool + coordinator，在 LangGraph 里可以映射成 StateGraph、conditional edges、tool executor node、checkpoint、interrupt/human approval、Send/Command 式并行分支和 supervisor/worker 子图。

1. State 是 QueryEngine

用一个 TypedDict/Pydantic state 保存 messages、cwd、工具权限、任务列表、worker 状态、transcript、token/预算、是否需要 compact、最后一次 tool_calls、错误和中断信号。LangGraph 的 checkpoint 用来替代 Claude Code transcript/resume 的一部分能力。

2. LLM node 是 query() 的模型调用

call_model 节点读取 state.messages 和 system context，调用带工具绑定的模型。如果返回 tool_calls，就走工具分支；如果没有 tool_calls，就进入 stop-hook/verification/final 分支。

3. Tool node 是 toolOrchestration

execute_tools 节点负责 schema 校验、权限判断、hook、真正执行工具、把 tool_result 追加回 messages。读类工具可以并行，写类工具按资源锁串行。

4. Supervisor 是 coordinator

复杂任务不要让一个 agent 顺序做完，而是让 supervisor 节点先拆任务，给 research / implementation / verification worker 子图发任务，再综合结果决定继续、重试、停止还是汇报。

一张比较接近 Claude Code 的 LangGraph 图可以这样设计：

START
  -> ingest_user_input
  -> load_context_and_memory
  -> maybe_compact
  -> supervisor_or_call_model
      -> if normal single-agent turn: call_model
      -> if complex task: plan_and_dispatch_workers

call_model
  -> if tool_calls: permission_and_hooks
  -> if final_answer: stop_hooks_or_finish

permission_and_hooks
  -> execute_tools
  -> append_tool_results
  -> maybe_compact
  -> call_model

plan_and_dispatch_workers
  -> research_worker(s) in parallel
  -> synthesize_findings
  -> implementation_worker
  -> verification_worker
  -> final_report

设计时最关键的是把“节点职责”切干净：

ingest_user_input：解析用户输入、slash command、文件附件、环境信息，写入 state.messages。
load_context_and_memory：加载项目说明、rules、memory、git status、MCP/tool registry，形成 system/user context。
maybe_compact：检查 token 预算；如果超限，调用 summary/compact 节点，把旧消息压缩成 compact boundary。
call_model：让模型决定下一步：回答、调用工具、请求子代理、进入 plan mode、或要求用户确认。
permission_and_hooks：对 tool call 做 schema 校验、policy 判断、pre-hook、人类审批 interrupt、输入改写。
execute_tools：按工具并发安全性执行；读操作可 fan-out，写操作按文件路径加锁。
worker_subgraph：每个 worker 是一个独立子图，有自己的 messages、tools、cwd、权限和 checkpoint。
synthesize/final：supervisor 综合 worker 输出，生成下一轮 worker prompt 或最终给用户的报告。

from typing import TypedDict, Annotated
from langgraph.graph import StateGraph, START, END
from langgraph.graph.message import add_messages
from langgraph.types import Command, Send, interrupt

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]
    cwd: str
    permission_mode: str
    tool_calls: list
    worker_results: list
    todos: list
    compact_needed: bool
    final: str | None

async def call_model(state: AgentState):
    response = await model_with_tools.ainvoke(state["messages"])
    return {"messages": [response], "tool_calls": response.tool_calls}

def route_after_model(state: AgentState):
    if state.get("tool_calls"):
        return "permission_and_hooks"
    return "stop_hooks_or_finish"

async def permission_and_hooks(state: AgentState):
    for call in state["tool_calls"]:
        if is_risky(call):
            decision = interrupt({"kind": "permission", "tool_call": call})
            if decision["action"] != "allow":
                return {"messages": [make_denial_result(call)]}
    return {}

async def execute_tools(state: AgentState):
    results = await run_read_tools_parallel_write_tools_serial(state["tool_calls"])
    return {"messages": results, "tool_calls": []}

def dispatch_workers(state: AgentState):
    tasks = decompose_task(state["messages"])
    return [Send("worker_subgraph", {"messages": [task.prompt], "cwd": state["cwd"]}) for task in tasks]

graph = StateGraph(AgentState)
graph.add_node("call_model", call_model)
graph.add_node("permission_and_hooks", permission_and_hooks)
graph.add_node("execute_tools", execute_tools)
graph.add_node("worker_subgraph", worker_graph)
graph.add_node("synthesize", synthesize_worker_results)

graph.add_edge(START, "call_model")
graph.add_conditional_edges("call_model", route_after_model)
graph.add_edge("permission_and_hooks", "execute_tools")
graph.add_edge("execute_tools", "call_model")
graph.add_edge("synthesize", END)
app = graph.compile(checkpointer=checkpointer)

权限怎么做

Claude Code 的权限系统在工具执行前。LangGraph 里应单独建 permission_and_hooks 节点：先走 policy/allowlist，再用 interrupt() 做 human-in-the-loop 审批，批准后把可能被用户修改的 input 写回 state。

并发怎么做

Claude Code 会并发跑 concurrency-safe 工具。LangGraph 里可以把只读工具拆成多个 Send 分支，或者在一个 executor 节点内部用 asyncio 并发；写工具则按 file_path / resource key 加锁串行。

子代理怎么做

每个 worker 用一个子图：自己的 state、system prompt、tool pool、checkpoint namespace。Supervisor 只拿 worker summary，不把所有原始工具输出塞回主上下文，避免污染主 agent。

恢复怎么做

用 checkpointer 保存每个 turn 的 state；长任务、worker、人工审批都可以恢复。对于工具副作用，要额外记录 tool_call_id、幂等键、文件快照或 patch，避免 resume 后重复执行危险写操作。

设计原则：LangGraph 负责“可控状态机”，LLM 只负责“决策下一步”。把权限、并发、子代理、压缩、恢复都放进显式节点，不要藏在 prompt 里；这样才接近 Claude Code 那种可恢复、可审计、可并行、可人工接管的工作流编排。
